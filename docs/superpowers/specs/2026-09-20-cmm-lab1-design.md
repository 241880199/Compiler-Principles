## 1. 目标与范围

编写一个程序，对 C-- 语言源代码做词法分析与语法分析，打印分析结果或错误信息。

### 1.1 必做

| 项 | 要求 |
|---|---|
| 错误类型 A | 词法错误：出现 C-- 词法未定义的字符，或不符合词法单元定义的字符 |
| 错误类型 B | 语法错误 |
| 语法树打印 | 无错时按先序打印全部结点，子结点缩进 2 空格 |

### 1.2 选做（全部实现）

| 项 | 内容 | 非法输入的处理 |
|---|---|---|
| 1.1 | 识别八进制 / 十六进制数 | `09`、`0x3G` → **type A** |
| 1.2 | 识别指数形式浮点数 | `1.05e` → **type A** |
| 1.3 | 滤除 `//` 与 `/*…*/` 注释 | 未闭合注释 → **type A** |

**关于非法数字为何报 type A**：按附录 A 的定义，`09` 既不匹配十进制整数（除 `0`
外首位不为 0）、也不匹配八进制（含 `9`）、也不匹配十六进制（不以 `0x` 开头），
`0x3G` 与 `1.05e` 同理——三者**不属于任何词法单元**，按实验要求 2.1.1 第 1 条即为
错误类型 A。要求书样例 2/样例 4 给出的 type B 备选答案，是在迁就一个**未实现校验**
的简易词法分析器（`09` 被朴素切成 `0` 和 `9`，错误顺延到语法阶段暴露），并非认为
该错误的分类存在歧义。

### 1.3 明确不做（YAGNI）

- 语义分析、符号表、类型检查 → 属于实验二
- `#include` / 预处理指令 → C-- 文法中不存在
- 多个输入文件 → 只接受单个文件名参数
- 注释嵌套支持 → C-- 明确**不**支持嵌套，嵌套是错误

## 3. 架构与数据流

```
test.cmm ──► [lexical.l / Flex] ──token(Node*)流──► [syntax.y / Bison] ──► AST 根
                    │                                      │
              维护 yylineno                         建树 + 错误恢复
                    │                                      │
              type A 错误 ─────────────────────────►  type B 错误
                                                           │
                                                    ┌──────┴──────┐
                                                    │  有错？      │
                                                    └──────┬──────┘
                                                     是 ───┴─── 否
                                                     │            │
                                            只打印错误信息   tree.c 先序打印
                                            （不打印语法树）
```

**核心决策：`YYSTYPE` 就是 `Node *`。**

因为采用统一 Node，终结符与非终结符**同构**——词法单元由 lexer 造好 `Node*` 交给
parser，语法单元在 action 里用 `newNode(...)` 组装。带来的直接好处：

1. 打印器面对**完全同质的树**，不需要"终结符走一条分支、非终结符走另一条"，遍历
   代码只有一份；
2. 不需要 `%union`，也不需要为每种终结符定义不同的语义值类型；
3. 实验二加符号表字段时，只需给 `Node` 加字段，遍历代码不动。

## 4. 数据结构

`src/tree.h` —— 全项目唯一的数据结构：

```c
typedef enum { NODE_GRAMMAR, NODE_TOKEN } NodeKind;

typedef struct Node {
    NodeKind      kind;    /* 终结符 / 非终结符 —— 打印行为不同，必须显式区分 */
    const char   *name;    /* "Program" / "ID" / "TYPE" / "INT" ... */
    int           line;    /* 见 §4.1 */
    const char   *lexeme;  /* 仅 ID / TYPE / INT / FLOAT 使用，其余为 NULL */
    int           nchild;
    struct Node **child;   /* 子节点数组 */
} Node;
```

`kind` 字段不可省。`printTree` 对两类结点的输出格式不同（终结符打 `NAME: 值`、
非终结符打 `NAME (行号)`），而**没有任何间接特征能可靠区分二者**：`SEMI`、`LP`、
`RP` 等终结符没有词素（`lexeme` 为 NULL，与 ε 结点相同），ε 结点又是 `nchild == 0`
（与终结符相同）。靠推测会静默出错，故显式声明。

### 4.1 行号与 ε 的求法（同一个函数）

要求书对行号的定义是"该语法单元产生出的所有词素中**第一个**在输入文件中出现的行号"。

**不**在每个 action 里单独赋行号，而是在打印时递归推导：

```c
/* 返回子树中第一个词法单元的行号；整棵子树不含词法单元时返回 0。 */
static int nodeLine(const Node *n) {
    if (n->kind == NODE_TOKEN) return n->line;   /* 词法单元：lexer 写入 */
    for (int i = 0; i < n->nchild; i++) {
        int l = nodeLine(n->child[i]);
        if (l > 0) return l;                     /* 第一个有行号的后代 */
    }
    return 0;                                    /* 子树不含任何词法单元 */
}
```

理由：词法单元的行号**只由 lexer 写入一次**，是唯一可信来源；语法单元的行号由结构
**推导**得出，不依赖任何 action 是否记得赋值。这消除了"某个产生式的 action 忘了写
行号"这一整类 bug。

**关键：返回值 0 同时就是 ε 的判定。**

要求书说"该语法单元产生了 ε 则无需打印"。"产生 ε" ⟺ 该单元推不出任何词素 ⟺
**其整棵子树不含词法单元** ⟺ `nodeLine` 返回 0。二者是同一件事，不需要第二个标志位。

常见错法是用 `nchild == 0` 判 ε，这是**错的**：`Program → ExtDefList → ε` 时
`Program` 有一个子结点，按 `nchild == 0` 会被误判为非 ε，从而打印出 `Program (0)`
——而行号 0 本身就已经暴露了它其实是 ε。**用 `nodeLine == 0` 判定则天然正确。**

### 4.2 接口

```c
Node *newNode(const char *name, int line, int nchild, ...);  /* 变参构造 */
Node *newToken(const char *name, int line, const char *lexeme);
void  printTree(Node *root, int depth);                      /* 先序打印 */
```

`printTree` 的规则（对应要求书 2.1.3）：

| 情形 | 输出 |
|---|---|
| 语法单元，未产生 ε | `<缩进><Name> (<line>)` |
| 语法单元，产生了 ε | **不输出** |
| 词法单元 | `<缩进><NAME>` |
| 词法单元 ID | `<缩进>ID: <lexeme>` |
| 词法单元 TYPE | `<缩进>TYPE: <int\|float>` |
| 词法单元 INT / FLOAT | `<缩进>INT: <十进制值>` |

缩进 = `depth * 2` 个空格，根结点 depth = 0。

**ε 判定的实现方式**：`kind == NODE_GRAMMAR && nodeLine(n) == 0` 即为 ε 结点，跳过
（判定依据见 §4.1）。

### 4.3 数值的十进制输出

`INT` 用 `strtol(s, NULL, 0)` ——**基数 0 让 C 库自动识别 `0` 前缀为八进制、
`0x` 前缀为十六进制**，无需手写进制转换：

| 源码 | `%d` 输出 | 要求书样例 |
|---|---|---|
| `1` | `1` | `INT: 1` ✅ |
| `0123` | `83` | `INT: 83` ✅ |
| `0x3F` | `63` | `INT: 63` ✅ |

`FLOAT` 用 `printf("%f", atof(s))`，6 位小数与样例一致：

| 源码 | `%f` 输出 | 要求书样例 |
|---|---|---|
| `3.5` | `3.500000` | `FLOAT: 3.500000` ✅ |
| `1.05e-4` | `0.000105` | `FLOAT: 0.000105` ✅ |

## 5. 词法分析器设计（`src/lexical.l`）

### 5.1 行号、选项与换行符容忍

```
%option yylineno
%option noyywrap
```

**必须容忍 `\r`（CRLF 行尾）**。flex 的 `.` 匹配除 `\n` 外的任意字符，若输入文件是
Windows 行尾，每个 `\r` 都会落到兜底规则上被报成 `Mysterious character`，导致**整个
文件全错**。而助教的测试文件用什么行尾不可控，故无论测试文件是否带 `\r` 都必须正常
工作：

- 空白规则写成 `[ \t\r]+`（**不含 `\n`**，让 flex 的 `yylineno` 自行计数换行）
- 其他需要跨字符匹配的规则（注释、字符串）内部也需容纳 `\r`

仓库内所有文本文件由 `.gitattributes` 强制 LF（见项目根目录），但**程序本身不能
假设输入是 LF**——这两件事要分开做，不能只做其中一件当保险。

### 5.2 正则定义

```
DIGIT   [0-9]
HEX     [0-9a-fA-F]
LETTER  [_a-zA-Z]
ID      {LETTER}({LETTER}|{DIGIT})*
OCT     0[0-7]+
HEXNUM  0[xX]{HEX}+
DEC     0|[1-9]{DIGIT}*
```

### 5.3 非法数字的检出：最长匹配抢优先权

Flex 的规则是**最长匹配优先，等长时先出现的规则优先**。利用"最长匹配"，让"疑似
非法"的模式比对应合法模式匹配得更长，从而抢到匹配权，再在 action 内校验。

**全部三类均设计为「单一规则 + action 内分支」，不依赖规则书写顺序。**

**八进制** —— 规则 `0{DIGIT}+`（比 `DEC` 的 `0` 长）：

| 输入 | 匹配者 | 长度 | action 内校验 | 结果 |
|---|---|---|---|---|
| `0123` | `0{DIGIT}+` | 4（`DEC` 的 `0` 仅 1） | 全 ≤7 → 合法 | `INT: 83` |
| `09` | `0{DIGIT}+` | 2（`DEC` 的 `0` 仅 1） | 含 `9` → 非法 | type A |
| `0` | `DEC` 的 `0` | 1 | `0{DIGIT}+` 需 ≥1 位后续数字，不匹配 | `INT: 0` |

**十六进制** —— 规则 `0[xX]({LETTER}|{DIGIT})+`：

> 此处必须用 `({LETTER}|{DIGIT})+` 而非 `{LETTER}+`。`LETTER` 是 `[_a-zA-Z]`，
> **不含数字**，若写成 `0[xX]{LETTER}+`，对 `0x3F` 只能匹配到 3 个字符，比合法规则
> `0[xX]{HEX}+`（4 个字符）**更短**，会被合法规则抢走，`G` 类的非法字符则永远
> 检测不到。这是本设计中最隐蔽的一个坑。

| 输入 | 匹配者 | 长度 | action 内校验 | 结果 |
|---|---|---|---|---|
| `0x3F` | 本规则 | 4 | 全为 HEX → 合法 | `INT: 63` |
| `0x3G` | 本规则 | 4（合法规则 `0[xX]{HEX}+` 只能匹配 `0x3`=3） | `G` 非 HEX → 非法 | type A |
| `0x` | 本规则 | 2 | `+` 需 ≥1 位后续字符，不匹配 → 回退 | `INT: 0` + `ID: x` |

**指数浮点数** —— 两条规则，长度天然可分，无需顺序依赖：

```
FLOATBASE   ({DIGIT}+\.{DIGIT}*|\.{DIGIT}+)
LEGAL_EXP   {FLOATBASE}[eE][+-]?{DIGIT}+
BROKEN_EXP  {FLOATBASE}[eE][+-]?
```

| 输入 | 匹配者 | 长度 | action 内校验 | 结果 |
|---|---|---|---|---|
| `1.05e-4` | `LEGAL_EXP` | 7 | — | `FLOAT: 0.000105` |
| `1.05e4` | `LEGAL_EXP` | 6（`BROKEN_EXP` 仅 5） | — | 合法 |
| `1.05e` | `BROKEN_EXP` | 5（长于纯 FLOAT 的 `1.05`=4） | 下一字符非 DIGIT → 非法 | type A |

> `BROKEN_EXP` 与 `LEGAL_EXP` 的先后顺序不影响正确性：合法输入下 `LEGAL_EXP` 必然
> 更长，非法输入下 `LEGAL_EXP` 根本不匹配。二者**无需**相互顾忌顺序。

### 5.4 注释

| 情形 | 实现 | 处理 |
|---|---|---|
| `//` 到行尾 | 规则 `"//"[^\n]*` | 丢弃 |
| `/*…*/` | 起始条件 `%x COMMENT`：`"/*"` 进入，`<COMMENT>"*/"` 退出，中间字符丢弃 | 丢弃 |
| 未闭合 `/*` | `<COMMENT><<EOF>>` | **type A**，行号= `/*` 所在行（回推算法见 §5.6） |
| 嵌套 `/* /* */ */` | 无需特殊处理 | 第一个 `*/` 即闭合，其后残留的 `*/` 变成游离的 `STAR` `DIV`，由语法分析器报 **type B** |

嵌套注释**不做特殊检测**——要求书样例 6 明确期望它自然退化为 type B 的语法错误。
起始条件天然实现了"第一个 `*/` 即闭合"的 C 语义，这正是所需行为。

### 5.5 兜底

规则表最后加一条 `.` → 报 type A `Mysterious character '<c>'`，覆盖所有未定义的
单字符（如样例 1 的 `~`）。

### 5.5.1 实测验证结论（flex 2.6.4）

以下行为已用原型实测确认，实现时直接照此书写：

| 场景 | 实测结果 |
|---|---|
| 未闭合注释 | 用起始条件 `%x COMMENT` + `<COMMENT><<EOF>>`，在 EOF 处报 type A，**行号回推为 `/*` 所在行**（实测报第 3 行而非文件末行）；`<<EOF>>` 动作里 `return 0` **立即终止**，不再对注释后的内容产生连锁误报。**返回前必须 `BEGIN(INITIAL)` 复位** —— 起始条件是全局状态，不复位则后续每次 `yylex()` 都会重复报同一条错误（语法分析器在错误恢复期间会反复调用 `yylex()`，届时必现） |
| 嵌套注释 | 注释在**第一个** `*/` 处闭合（符合 C 语义），其后残留的 `*/` 正常切成 `DIV` `STAR` 两个词法单元 → 交由语法分析器报 type B。与要求书样例 6 的期望一致 |
| CRLF 输入 | 空白规则含 `\r` 后，**行号完全正确且无 `\r` 误报** |
| 多行注释后的行号 | flex 自动维护正确（见 §5.6） |

**起始条件（`%x COMMENT`）而非单条大正则**是本节的实现选择：它能在 EOF 处精确报出
未闭合注释，且天然实现"第一个 `*/` 即闭合"的非嵌套语义，不需要额外的正则技巧。

### 5.6 行号机制（已实测确认，**不要手工计数**）

`%option yylineno` 由 flex 自动维护，且**当一条规则匹配的文本内部跨过 `\n` 时，
flex 会自动把跨过的换行数计入 `yylineno`**。

实测（flex 2.6.4，输入为 8 行、第 3–6 行是一个多行注释）：

```
ID 'main' at yylineno=1
NEWLINE rule, yylineno=3
BLOCKCOMMENT end, yylineno=6     ← 规则跨了 3 个换行，flex 自动加到 6
NEWLINE rule, yylineno=7
ID 'int' at yylineno=7           ← 第 7 行，正确
```

结论与两条纪律：

1. **绝不在 action 里手工 `yylineno += 换行数`** —— flex 已经加过了，手工再加会
   **重复计数**，把后续所有行号顶偏。这是本项目最容易"好心办坏事"的一处。
2. 规则匹配完成后，`yylineno` 是**该次匹配结束所在的行**。对跨多行的匹配（如未闭合
   注释），若要把错误报在**起始行**，需自行处理。**推荐做法**是在进入注释时就把行号
   存下来（实现见 §5.4 的 `commentStart`），比事后回推更直接：

   ```c
   /* 进入注释时 */
   commentStart = yylineno;
   /* 在 <COMMENT><<EOF>> 处 */
   reportError('A', commentStart, "Unterminated comment");
   ```

   另一种等价做法是事后按 `yytext` 中的换行数回推 `yylineno - nl`，但既然起始行在进入
   注释时是已知的，没必要再算一次。单行 token 无需任何处理（起始行 == 结束行）。

## 6. 语法分析器设计（`src/syntax.y`）

### 6.1 文法

完全照抄附录 A，**不增删任何产生式**（错误恢复产生式除外，见 §6.3）。

### 6.2 优先级与结合性

按附录 A 表 1，声明次序由低到高（Bison 中**后声明者优先级高**）：

```bison
%right ASSIGNOP                      /* 9 赋值 */
%left  OR                            /* 8 */
%left  AND                           /* 7 */
%left  RELOP                         /* 5,6 合并 —— 见下 */
%left  PLUS MINUS                    /* 4 */
%left  STAR DIV                      /* 3 */
%right NOT UMINUS                    /* 2 一元 */
```

两点说明：

1. **RELOP 不分级**。附录 A 脚注 5 说明：标准 C 中 `< <= > >=` 优先级高于 `== !=`，
   "在这里为了方便处理而将它们的优先级统一了"。且文法中本就是**单一产生式**
   `Exp → Exp RELOP Exp`，六种关系运算符天然同级，故只声明一个 `%left RELOP`。
2. **`UMINUS` 是伪 token**，用于消除 `Exp → MINUS Exp` 与 `Exp → Exp MINUS Exp` 的
   冲突，写法为 `Exp : MINUS Exp %prec UMINUS`。

`LP RP LB RB DOT` 无需参与冲突消解（`LP Exp RP`、`Exp LB Exp RB`、`Exp DOT ID`
均无歧义），故**不声明**，避免引入误导性的优先级。

### 6.2.1 预期内的良性冲突（**不要试图消除**）

以下冲突 Bison 会报告，但**默认的"移进"恰好就是正确答案**，干预反而会引入错误。
实现时以这份清单为准，凡是**不在此列**的新冲突才需要处理：

| # | 冲突位置 | 看什么 token | Bison 默认 | 为何正确 |
|---|---|---|---|---|
| 1 | `VarDec : ID .` vs `FunDec : ID . LP …` | `LP` | 移进 → FunDec | `int f() {}` 是函数；`int x` 后跟 `(` 不可能是变量 |
| 2 | `Exp : ID .` vs `Exp : ID . LP …` | `LP` | 移进 → 函数调用 | `f(x)` 是调用；`x` 后跟 `(` 不可能是变量引用 |
| 3 | `IF LP Exp RP Stmt .` vs `. ELSE Stmt` | `ELSE` | 移进 → else 就近匹配 | 这正是 C 语言的悬空 else 语义 |

这三处冲突**必须在报告/注释里写明是已知且正确的**，否则后续调 `.output` 时容易被
误导去"修"它们。

### 6.3 错误恢复

用 `error` 产生式让 Bison 能报告**多个**语法错误。基线集合：

```bison
Stmt   : ... | error SEMI      /* 语句层 */
CompSt : ... | error RC        /* 块层兜底 */
Exp    : ... | error RB        /* 下标层 */
```

**设计依据**（Bison 的恢复机制：进入错误模式后不断**弹出**栈顶状态直到能移进
`error`，弹出即意味着丢弃已匹配的语法单元）：

- 指导书提出的"error 后能跟的内容越多越好"与"丢弃 token 越少越好"这对矛盾，
  解法是**把 `error` 铺到各个语法层级**——Bison 总是弹最少的状态找最近的出口，
  出口越密，丢弃越少。二者不矛盾，而是同一手段的两个侧面。
- 三条产生式分别对应要求书样例的实际错误：
  - `Exp → error RB`：样例 2 行 5 `a[5,3]` —— 栈上是 `Exp LB Exp` 期望 `RB` 却见
    `COMMA`，只有 `Exp` 层有 `error` 出口才能在此处就地恢复，丢掉 `,` 和 `3` 两个
    token 后在 `]` 同步，语句后半段 `= 1.5;` 照常解析；
  - `Stmt → error SEMI`：样例 2 行 6 `if (...) i = 1 else i = 0;` —— 弹到
    `IF LP Exp RP . Stmt` 后移进 `error`，在行尾 `;` 同步，**恰好报 1 条**错误，
    与样例输出一致；
  - `Stmt → error SEMI`：样例 6 嵌套注释 —— 第 8 行残留的 `*/` 报 1 条错误并吞掉
    第 9 行。**这里只报 1 条才是正确的**，多报第 9 行的错反而与样例不符。

**`Exp → error RP` 暂不加入**：其风险是 `error` 后必须找到 `RP` 才能同步，而圆括号
失配时往往根本不存在 `RP`，会导致一直吞到文件尾、掩盖后续所有错误。此判断需要用
测试用例实测证伪，不能用推理定死。

**这份清单以实测为准，不以推理为准。** 实现后跑 `Test/sample/` 全套，按失败用例
增删同步点，并以 `bison -v` 生成的 `syntax.output` 检查新增冲突。

### 6.4 Bison 版本兼容

- 用 `%define api.value.type {Node *}` 而非 `%union`
- **不使用** `%define parse.error detailed`（Bison 3.0.4 不支持该值）
- 错误信息在 `yyerror` 中自行拼装，不依赖 Bison 的错误文本

## 7. 输出规范

### 7.1 有词法或语法错误时

**只**输出错误信息，**绝不**输出语法树。格式：

```
Error type A at Line 4: Mysterious character "~".
```

- 错误类型只能是 `A` 或 `B`
- 每条错误单独占一行
- 必须报告**全部**错误（同一行保证不出现多个错误）
- 说明文字内容不限，但**错误类型和行号必须正确**

### 7.2 无错误时

先序打印语法树，规则见 §4.2。

### 7.3 两种模式互斥的实现

用一个全局 `errorOccurred` 标志：`yyerror` 与词法错误处理函数置位。`main` 在
`yyparse()` 返回后检查该标志——置位则什么都不打印（错误已在过程中逐条输出），
未置位才调用 `printTree`。

## 9. 测试策略

**唯一验收标准：`Test/sample/` 下的期望输出必须与程序实际输出逐字节一致**——空格、
缩进、行号都不能差。

### 9.1 用例来源

1. **要求书样例**（必做 4 个 + 选做 6 个）：输入从 PDF 逐字抄录，期望输出**同样逐字
   手抄**，不从程序输出反填——否则测试就退化成"验证程序等于它自己"。
2. **自建边界用例**（`Test/err/`），针对本设计识别出的风险点：
   - 多行注释跨换行后的报错行号（§5.6 点名的最高风险项）
   - `0x3F`（等长规则顺序依赖）、`00`、`08`、`0x`
   - `1.05e+`、`.5E03`、`43.e-4`（附录 A 补充说明里给的合法指数形式）
   - 一个文件内多个错误、跨多行的多个错误
   - 空文件、只有注释的文件

### 9.2 执行

`scripts/run_tests.sh`：遍历 `Test/**/*.cmm`，比对同名 `.exp`，输出 diff 与汇总。
全部用例在 WSL 中运行。

## 10. 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 多行注释导致 `yylineno` 漏计 | 报错行号错误 → 直接失分 | §5.6 强制手工计数 + 专项用例 |
| 十六进制校验模式误写成 `{LETTER}+` | `0x3G` 检测不到，静默漏报 | §5.3 已写明必须用 `({LETTER}\|{DIGIT})+` + 专项用例 |
| `error` 产生式引入**清单外**的新冲突 | 可能改变正常语句的解析 | `bison -v` 检查 `syntax.output`，与 §6.2.1 清单比对 |
| Bison 3.8.2 与评分环境 3.0.4 的行为差异 | 评分机上编译失败 | §2.2 / §6.4 限定只用两版通用的写法 |
| 样例期望输出为手工抄录 | 抄错会导致"程序正确却测试失败" | 抄录后与 PDF 二次核对 |
| `printTree` 误判结点类型 | 输出格式整体错乱 | §4 显式 `kind` 字段，不靠推测 |
