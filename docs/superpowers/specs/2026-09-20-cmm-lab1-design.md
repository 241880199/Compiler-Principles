## 1. 目标与范围

编写一个程序，对 C-- 语言源代码做词法分析与语法分析，打印分析结果或错误信息。

### 1.1 必做

| 项 | 要求 |
|---|---|
| 错误类型 A | 词法错误：出现 C-- 词法未定义的字符，或不符合词法单元定义的字符 |
| 错误类型 B | 语法错误 |
| 语法树打印 | 无错时按先序打印全部结点，子结点缩进 2 空格 |

### 1.2 选做（全部实现）

| 项 | 内容 | 非法输入的处理 |
|---|---|---|
| 1.1 | 识别八进制 / 十六进制数 | `09`、`0x3G` → **type A** |
| 1.2 | 识别指数形式浮点数 | `1.05e` → **type A** |
| 1.3 | 滤除 `//` 与 `/*…*/` 注释 | 未闭合注释 → **type A** |

**关于非法数字为何报 type A**：按附录 A 的定义，`09` 既不匹配十进制整数（除 `0`
外首位不为 0）、也不匹配八进制（含 `9`）、也不匹配十六进制（不以 `0x` 开头），
`0x3G` 与 `1.05e` 同理——三者**不属于任何词法单元**，按实验要求 2.1.1 第 1 条即为
错误类型 A。要求书样例 2/样例 4 给出的 type B 备选答案，是在迁就一个**未实现校验**
的简易词法分析器（`09` 被朴素切成 `0` 和 `9`，错误顺延到语法阶段暴露），并非认为
该错误的分类存在歧义。

### 1.3 明确不做（YAGNI）

- 语义分析、符号表、类型检查 → 属于实验二
- `#include` / 预处理指令 → C-- 文法中不存在
- 多个输入文件 → 只接受单个文件名参数
- 注释嵌套支持 → C-- 明确**不**支持嵌套，嵌套是错误

## 3. 架构与数据流

```
test.cmm ──► [lexical.l / Flex] ──token(Node*)流──► [syntax.y / Bison] ──► AST 根
                    │                                      │
              维护 yylineno                         建树 + 错误恢复
                    │                                      │
              type A 错误 ─────────────────────────►  type B 错误
                                                           │
                                                    ┌──────┴──────┐
                                                    │  有错？      │
                                                    └──────┬──────┘
                                                     是 ───┴─── 否
                                                     │            │
                                            只打印错误信息   tree.c 先序打印
                                            （不打印语法树）
```

**核心决策：`YYSTYPE` 就是 `Node *`。**

因为采用统一 Node，终结符与非终结符**同构**——词法单元由 lexer 造好 `Node*` 交给
parser，语法单元在 action 里用 `newNode(...)` 组装。带来的直接好处：

1. 打印器面对**完全同质的树**，不需要"终结符走一条分支、非终结符走另一条"，遍历
   代码只有一份；
2. 不需要 `%union`，也不需要为每种终结符定义不同的语义值类型；
3. 实验二加符号表字段时，只需给 `Node` 加字段，遍历代码不动。

## 4. 数据结构

`src/tree.h` —— 全项目唯一的数据结构：

```c
typedef enum { NODE_GRAMMAR, NODE_TOKEN } NodeKind;

typedef struct Node {
    NodeKind      kind;    /* 终结符 / 非终结符 —— 打印行为不同，必须显式区分 */
    const char   *name;    /* "Program" / "ID" / "TYPE" / "INT" ... */
    int           line;    /* 见 §4.1 */
    const char   *lexeme;  /* 仅 ID / TYPE / INT / FLOAT 使用，其余为 NULL */
    int           nchild;
    struct Node **child;   /* 子节点数组 */
} Node;
```

`kind` 字段不可省。`printTree` 对两类结点的输出格式不同（终结符打 `NAME: 值`、
非终结符打 `NAME (行号)`），而**没有任何间接特征能可靠区分二者**：`SEMI`、`LP`、
`RP` 等终结符没有词素（`lexeme` 为 NULL，与 ε 结点相同），ε 结点又是 `nchild == 0`
（与终结符相同）。靠推测会静默出错，故显式声明。

### 4.1 行号与 ε 的求法（同一个函数）

要求书对行号的定义是"该语法单元产生出的所有词素中**第一个**在输入文件中出现的行号"。

**不**在每个 action 里单独赋行号，而是在打印时递归推导：

```c
/* 返回子树中第一个词法单元的行号；整棵子树不含词法单元时返回 0。 */
static int nodeLine(const Node *n) {
    if (n->kind == NODE_TOKEN) return n->line;   /* 词法单元：lexer 写入 */
    for (int i = 0; i < n->nchild; i++) {
        int l = nodeLine(n->child[i]);
        if (l > 0) return l;                     /* 第一个有行号的后代 */
    }
    return 0;                                    /* 子树不含任何词法单元 */
}
```

理由：词法单元的行号**只由 lexer 写入一次**，是唯一可信来源；语法单元的行号由结构
**推导**得出，不依赖任何 action 是否记得赋值。这消除了"某个产生式的 action 忘了写
行号"这一整类 bug。

**关键：返回值 0 同时就是 ε 的判定。**

要求书说"该语法单元产生了 ε 则无需打印"。"产生 ε" ⟺ 该单元推不出任何词素 ⟺
**其整棵子树不含词法单元** ⟺ `nodeLine` 返回 0。二者是同一件事，不需要第二个标志位。

常见错法是用 `nchild == 0` 判 ε，这是**错的**：`Program → ExtDefList → ε` 时
`Program` 有一个子结点，按 `nchild == 0` 会被误判为非 ε，从而打印出 `Program (0)`
——而行号 0 本身就已经暴露了它其实是 ε。**用 `nodeLine == 0` 判定则天然正确。**

### 4.2 接口

与 `src/tree.h` 逐字一致（原稿的签名是错的，已按实际代码更正）：

```c
Node *newNode(const char *name, int nchild, ...);      /* 变参构造；**不接受行号** */
Node *newToken(const char *name, int line, const char *lexeme);
void  printTree(const Node *root);                     /* 先序打印；**不接受 depth** */
```

两处与原稿的差异，各有原因：

- `newNode` **没有 `line` 形参**。语法单元的行号一律由 §4.1 的 `nodeLine()` 在打印时推导
  （`newNode` 把 `line` 固定写成 0），从签名上就杜绝了"某个 action 忘了传行号"。
- `printTree` **没有 `depth` 形参**。缩进是递归深度，由内部静态函数
  `printNode(const Node *, int depth)` 持有；对外只需给一个根结点。

`printTree` 的规则（对应要求书 2.1.3）：

| 情形 | 输出 |
|---|---|
| 语法单元，未产生 ε | `<缩进><Name> (<line>)` |
| 语法单元，产生了 ε | **不输出** |
| 词法单元 | `<缩进><NAME>` |
| 词法单元 ID | `<缩进>ID: <lexeme>` |
| 词法单元 TYPE | `<缩进>TYPE: <int\|float>` |
| 词法单元 INT / FLOAT | `<缩进>INT: <十进制值>` |

缩进 = `depth * 2` 个空格，根结点 depth = 0（`depth` 是内部递归函数 `printNode` 的参数，
不是对外接口的一部分，见上）。

**ε 判定的实现方式**：`kind == NODE_GRAMMAR && nodeLine(n) == 0` 即为 ε 结点，跳过
（判定依据见 §4.1）。

### 4.3 数值的十进制输出

`INT` 用 `strtol(s, NULL, 0)` ——**基数 0 让 C 库自动识别 `0` 前缀为八进制、
`0x` 前缀为十六进制**，无需手写进制转换：

| 源码 | `%d` 输出 | 要求书样例 |
|---|---|---|
| `1` | `1` | `INT: 1` ✅ |
| `0123` | `83` | `INT: 83` ✅ |
| `0x3F` | `63` | `INT: 63` ✅ |

`FLOAT` 用 `printf("%f", atof(s))`，6 位小数与样例一致：

| 源码 | `%f` 输出 | 要求书样例 |
|---|---|---|
| `3.5` | `3.500000` | `FLOAT: 3.500000` ✅ |
| `1.05e-4` | `0.000105` | `FLOAT: 0.000105` ✅ |

## 5. 词法分析器设计（`src/lexical.l`）

### 5.1 行号、选项与换行符容忍

```
%option yylineno
%option noyywrap
```

**必须容忍 `\r`（CRLF 行尾）**。flex 的 `.` 匹配除 `\n` 外的任意字符，若输入文件是
Windows 行尾，每个 `\r` 都会落到兜底规则上被报成 `Mysterious character`，导致**整个
文件全错**。而助教的测试文件用什么行尾不可控，故无论测试文件是否带 `\r` 都必须正常
工作：

- 空白规则写成 `[ \t\r]+`（**不含 `\n`**，让 flex 的 `yylineno` 自行计数换行）
- 其他需要跨字符匹配的规则（注释、字符串）内部也需容纳 `\r`

仓库内所有文本文件由 `.gitattributes` 强制 LF（见项目根目录），但**程序本身不能
假设输入是 LF**——这两件事要分开做，不能只做其中一件当保险。

### 5.2 正则定义

```
DIGIT   [0-9]
HEX     [0-9a-fA-F]
LETTER  [_a-zA-Z]
ID      {LETTER}({LETTER}|{DIGIT})*
OCT     0[0-7]+
HEXNUM  0[xX]{HEX}+
DEC     0|[1-9]{DIGIT}*
```

### 5.3 非法数字的检出：最长匹配抢优先权

Flex 的规则是**最长匹配优先，等长时先出现的规则优先**。利用"最长匹配"，让"疑似
非法"的模式比对应合法模式匹配得更长，从而抢到匹配权，再在 action 内校验。

**全部三类均设计为「单一规则 + action 内分支」，不依赖规则书写顺序。**

**八进制** —— 规则 `0{DIGIT}+`（比 `DEC` 的 `0` 长）：

| 输入 | 匹配者 | 长度 | action 内校验 | 结果 |
|---|---|---|---|---|
| `0123` | `0{DIGIT}+` | 4（`DEC` 的 `0` 仅 1） | 全 ≤7 → 合法 | `INT: 83` |
| `09` | `0{DIGIT}+` | 2（`DEC` 的 `0` 仅 1） | 含 `9` → 非法 | type A |
| `0` | `DEC` 的 `0` | 1 | `0{DIGIT}+` 需 ≥1 位后续数字，不匹配 | `INT: 0` |

**十六进制** —— 规则 `0[xX]({LETTER}|{DIGIT})+`：

> 此处必须用 `({LETTER}|{DIGIT})+` 而非 `{LETTER}+`。`LETTER` 是 `[_a-zA-Z]`，
> **不含数字**，若写成 `0[xX]{LETTER}+`，对 `0x3F` 只能匹配到 3 个字符，比合法规则
> `0[xX]{HEX}+`（4 个字符）**更短**，会被合法规则抢走，`G` 类的非法字符则永远
> 检测不到。这是本设计中最隐蔽的一个坑。

| 输入 | 匹配者 | 长度 | action 内校验 | 结果 |
|---|---|---|---|---|
| `0x3F` | 本规则 | 4 | 全为 HEX → 合法 | `INT: 63` |
| `0x3G` | 本规则 | 4（合法规则 `0[xX]{HEX}+` 只能匹配 `0x3`=3） | `G` 非 HEX → 非法 | type A |
| `0x` | 本规则 | 2 | `+` 需 ≥1 位后续字符，不匹配 → 回退 | `INT: 0` + `ID: x` |

**指数浮点数** —— 两条规则，长度天然可分，无需顺序依赖：

```
FLOATBASE   ({DIGIT}+\.{DIGIT}*|\.{DIGIT}+)
LEGAL_EXP   {FLOATBASE}[eE][+-]?{DIGIT}+
BROKEN_EXP  {FLOATBASE}[eE][+-]?
```

| 输入 | 匹配者 | 长度 | action 内校验 | 结果 |
|---|---|---|---|---|
| `1.05e-4` | `LEGAL_EXP` | 7 | — | `FLOAT: 0.000105` |
| `1.05e4` | `LEGAL_EXP` | 6（`BROKEN_EXP` 仅 5） | — | 合法 |
| `1.05e` | `BROKEN_EXP` | 5（长于纯 FLOAT 的 `1.05`=4） | 下一字符非 DIGIT → 非法 | type A |

> `BROKEN_EXP` 与 `LEGAL_EXP` 的先后顺序不影响正确性：合法输入下 `LEGAL_EXP` 必然
> 更长，非法输入下 `LEGAL_EXP` 根本不匹配。二者**无需**相互顾忌顺序。

### 5.4 注释

| 情形 | 实现 | 处理 |
|---|---|---|
| `//` 到行尾 | 规则 `"//"[^\n]*` | 丢弃 |
| `/*…*/` | 起始条件 `%x COMMENT`：`"/*"` 进入，`<COMMENT>"*/"` 退出，中间字符丢弃 | 丢弃 |
| 未闭合 `/*` | `<COMMENT><<EOF>>` | **type A**，行号= `/*` 所在行（回推算法见 §5.6） |
| 嵌套 `/* /* */ */` | 无需特殊处理 | 第一个 `*/` 即闭合，其后残留的 `*/` 变成游离的 `STAR` `DIV`，由语法分析器报 **type B** |

嵌套注释**不做特殊检测**——要求书样例 6 明确期望它自然退化为 type B 的语法错误。
起始条件天然实现了"第一个 `*/` 即闭合"的 C 语义，这正是所需行为。

### 5.5 兜底

规则表最后加一条 `.` → 报 type A `Mysterious character '<c>'`，覆盖所有未定义的
单字符（如样例 1 的 `~`）。

### 5.5.1 实测验证结论（flex 2.6.4）

以下行为已用原型实测确认，实现时直接照此书写：

| 场景 | 实测结果 |
|---|---|
| 未闭合注释 | 用起始条件 `%x COMMENT` + `<COMMENT><<EOF>>`，在 EOF 处报 type A，**行号回推为 `/*` 所在行**（实测报第 3 行而非文件末行）；`<<EOF>>` 动作里 `return 0` **立即终止**，不再对注释后的内容产生连锁误报。**返回前必须 `BEGIN(INITIAL)` 复位** —— 起始条件是全局状态，不复位则后续每次 `yylex()` 都会重复报同一条错误（语法分析器在错误恢复期间会反复调用 `yylex()`，届时必现） |
| 嵌套注释 | 注释在**第一个** `*/` 处闭合（符合 C 语义），其后残留的 `*/` 正常切成 `DIV` `STAR` 两个词法单元 → 交由语法分析器报 type B。与要求书样例 6 的期望一致 |
| CRLF 输入 | 空白规则含 `\r` 后，**行号完全正确且无 `\r` 误报** |
| 多行注释后的行号 | flex 自动维护正确（见 §5.6） |

> ⚠️ **本节的实测是在纯词法原型（`Test/unit/test_lexer`）上做的，它不跑语法分析器。**
> 因此"未闭合注释只产生一条 type A"这个结论**只在词法层成立**。端到端实测：
> 若 `/*` 位于一个**永远无法闭合的函数体内**，语法分析器还会额外报一条 type B
> （行号停在最后真正发出的词法单元，因为 `curTokenLine` 只在 `emit()` 里更新，
> 而 `<<EOF>>` 是直接 `return 0`）。
>
> **教训：词法层测过的行为，不等于端到端的行为。** 单测覆盖了某个模块，不代表该
> 模块在完整流水线里的表现已被覆盖 —— 两者的差别恰恰是集成层引入的错误。

**起始条件（`%x COMMENT`）而非单条大正则**是本节的实现选择：它能在 EOF 处精确报出
未闭合注释，且天然实现"第一个 `*/` 即闭合"的非嵌套语义，不需要额外的正则技巧。

### 5.6 行号机制（已实测确认，**不要手工计数**）

`%option yylineno` 由 flex 自动维护，且**当一条规则匹配的文本内部跨过 `\n` 时，
flex 会自动把跨过的换行数计入 `yylineno`**。

实测（flex 2.6.4，输入为 8 行、第 3–6 行是一个多行注释）：

```
ID 'main' at yylineno=1
NEWLINE rule, yylineno=3
BLOCKCOMMENT end, yylineno=6     ← 规则跨了 3 个换行，flex 自动加到 6
NEWLINE rule, yylineno=7
ID 'int' at yylineno=7           ← 第 7 行，正确
```

结论与两条纪律：

1. **绝不在 action 里手工 `yylineno += 换行数`** —— flex 已经加过了，手工再加会
   **重复计数**，把后续所有行号顶偏。这是本项目最容易"好心办坏事"的一处。
2. 规则匹配完成后，`yylineno` 是**该次匹配结束所在的行**。对跨多行的匹配（如未闭合
   注释），若要把错误报在**起始行**，需自行处理。**推荐做法**是在进入注释时就把行号
   存下来（实现见 §5.4 的 `commentStart`），比事后回推更直接：

   ```c
   /* 进入注释时 */
   commentStart = yylineno;
   /* 在 <COMMENT><<EOF>> 处 */
   reportError('A', commentStart, "Unterminated comment");
   ```

   另一种等价做法是事后按 `yytext` 中的换行数回推 `yylineno - nl`，但既然起始行在进入
   注释时是已知的，没必要再算一次。单行 token 无需任何处理（起始行 == 结束行）。

## 6. 语法分析器设计（`src/syntax.y`）

### 6.1 文法

完全照抄附录 A，**不增删任何产生式**（错误恢复产生式除外，见 §6.3）。

### 6.2 优先级与结合性

按附录 A 表 1，声明次序由低到高（Bison 中**后声明者优先级高**）：

```bison
%right ASSIGNOP                      /* 9 赋值 */
%left  OR                            /* 8 */
%left  AND                           /* 7 */
%left  RELOP                         /* 5,6 合并 —— 见下 */
%left  PLUS MINUS                    /* 4 */
%left  STAR DIV                      /* 3 */
%right NOT UMINUS                    /* 2 一元 */
```

两点说明：

1. **RELOP 不分级**。附录 A 脚注 5 说明：标准 C 中 `< <= > >=` 优先级高于 `== !=`，
   "在这里为了方便处理而将它们的优先级统一了"。且文法中本就是**单一产生式**
   `Exp → Exp RELOP Exp`，六种关系运算符天然同级，故只声明一个 `%left RELOP`。
2. **`UMINUS` 是伪 token**，用于消除 `Exp → MINUS Exp` 与 `Exp → Exp MINUS Exp` 的
   冲突，写法为 `Exp : MINUS Exp %prec UMINUS`。

**`LB` 与 `DOT` 必须声明为最高优先级。** 原稿写"`LP Exp RP`、`Exp LB Exp RB`、
`Exp DOT ID` 均无歧义，故不声明"——**这是事实错误**，已删除。真实歧义是：

> 栈上 `Exp PLUS Exp •` 遇前瞻 `LB`：
> 归约得 `(a + b)[1]`，移进得 `a + (b[1])`，**两棵树都合法** ⇒ 真实的 shift/reduce 冲突。

Bison 只在**规则与前瞻 token 都声明了优先级**时才用优先级消解。`LB`/`DOT` 不声明，
这类冲突**根本不进入优先级判定**，声明多少其他运算符都消不掉。实测：声明其余运算符后
`Exp` 的 100 处冲突只消掉 80 处，剩下 20 处正是 `LB`/`DOT` 引起的
（10 个 state × 2 个 token）。

`LP` 则确实无需声明：`LP ∉ Follow(Exp)`（`LP Exp RP` 中的 `LP` 在 Exp **之前**），
不构成冲突。同理 `RB` 也不需要 —— `Exp : Exp LB Exp RB` 归约完成后 Exp 即完整，
无可移进项与之竞争。

在附录 A 表 1 中，`[ ]` 与 `.` 本就属于优先级最高的第 1 级（"括号或函数调用、数组访问、
结构体访问"），与 C 语言一致。**声明它们是以显式优先级表正确建模 C 的语义，不是为消
冲突而加的权宜之计**，且结果与 Bison 默认移进完全一致（语义中性）。

### 6.2.1 冲突的预期（**实测修正版**）

> ⚠️ **本节曾写错，已按实测更正。** 原稿断言"以下三处 Bison 会报 shift/reduce 冲突，
> 默认移进恰好正确"。实测（bison 3.8.2，Task 4 阶段）：**`grep -c conflict syntax.output`
> 的结果是 0**，三处里有两处根本没有被报成冲突。原判断是按 SLR 直觉推演的，而 Bison
> 生成的是 **LALR(1)**，前瞻集能把它们直接分开。

**实测观察**（`syntax.output` state 13）：

```
State 13

   16 VarDec: ID •
   19 FunDec: ID • LP RP

    LP  shift, and go to state 19

    $default  reduce using rule 16 (VarDec)
```

`VarDec : ID •` 与 `FunDec : ID • LP RP` 可以并存而**不构成冲突**，因为
`LP ∉ Follow(VarDec)` —— 两者的前瞻集不相交，遇 `LP` 只有移进一种选择。同理
`OptTag : ID •` / `Tag : ID •` 由 `LC` 与否区分开。

**所以正确的预期是**：

| 位置 | 是否报冲突 | 说明 |
|---|---|---|
| `VarDec : ID .` vs `FunDec : ID . LP …` | **否** | `LP ∉ Follow(VarDec)`，LALR 前瞻集已分开 |
| `Exp : ID .` vs `Exp : ID . LP …` | **否** | 同理，`LP ∉ Follow(Exp)` |
| `IF LP Exp RP Stmt .` vs `. ELSE Stmt` | **是**（悬空 else） | `ELSE ∈ Follow(Stmt)`，两者前瞻集确实相交，这是**唯一**的真实冲突；Bison 默认移进 = else 就近匹配，正是 C 语义，**保持默认即可** |

**实现时的验收标准**：声明优先级**之后**，`syntax.output` 中出现的冲突应当**只有悬空
else 一处**。**凡出现上述两处"看似该冲突"的 state，说明前瞻集没能分开——那是真问题，
要查文法是否有别的错误，而不是去加优先级掩盖。**

> ⚠️ **上一条验收标准在本项目后续被修正为「恰好 3 处」**：采纳 `Def : error`
> （§6.3）后，除了悬空 else 还多出 2 处 `DefList` 可空引起的冲突。**归属仍是明确的**
> —— State 26 `CompSt: LC • DefList StmtList RC`、State 31 `DefList: Def • DefList`、
> State 114 悬空 else，全部 `1 shift/reduce`，无 reduce/reduce。
> `StructSpecifier : STRUCT OptTag LC • DefList RC`（State 20）**不在其列**：结构体
> 成员表后只能跟 `RC`，`error` 不进其前瞻集，那里的 `error` 是无歧义的移进。
> 所以本节的原则不变（"**看归属，不是看数量**"），只是当前应有的数量是 **3**。

### 6.2.2 声明优先级**之前**的冲突数（Task 5 阶段，实测）

⚠️ **这一段是实测补充，不是本节原稿内容。** Task 5 做完后实测：

```
11 个冲突 state、101 处 shift/reduce、0 处 reduce/reduce
```

其中：

| 来源 | 处数 | 说明 |
|---|---|---|
| 悬空 else | **1** | State 107，`Stmt : IF LP Exp RP Stmt •` vs `| … • ELSE Stmt` |
| `Exp` 歧义 | **100** | 8 条二元 `Exp` 规则（rule 39–46）各 10 处，`MINUS Exp`、`NOT Exp` 各 10 处 |

**这 100 处是 Task 5 刻意不声明优先级的必然结果**：`Exp : Exp PLUS Exp` 在无优先级时是
**本质歧义**，LALR(1) 的前瞻集分不开（冲突数与输入无关，是文法本身的性质）。它们正是
Task 6 要消除的对象。

**所以冲突数的预期取决于阶段**：

| 阶段 | 冲突数 | 构成 |
|---|---|---|
| Task 5（无任何优先级声明） | **101** | 100 `Exp` + 1 悬空 else |
| Task 6 只声明 `ASSIGNOP`…`NOT`/`UMINUS`（**漏掉 `LB`/`DOT`**） | **21** | 20（`LB`/`DOT` 引起）+ 1 悬空 else |
| Task 6 完整声明（**含 `LB`/`DOT`**，见 §6.2） | **1** | 只剩悬空 else |
| **后续追加 `Def : error` 之后**（当前状态，见 §6.3） | **3** | 悬空 else 1 + `Def : error` 2 |

⚠️ **中间那一行是关键**：只声明其余运算符时，`Exp` 的 100 处只消掉 80 处，剩下 20 处
**消不掉** —— 因为 `LB`/`DOT` 没声明优先级，`Exp PLUS Exp •` 遇 `LB` 这类冲突根本不进入
优先级判定。**这 20 处不会自动消失，必须显式声明 `LB`/`DOT` 才能收敛到 1。**
（原稿只写"声明优先级后剩 1 处"，漏了这一层，实测才发现。）

**不要为了把 Task 5 的 101 处"消到 1"而提前声明优先级** —— 那是 Task 6 的事。判据是
**冲突的归属**（是否全在 `Exp`、`LB`/`DOT` 与悬空 else 上），不是**冲突的数量**。

### 6.3 错误恢复

用 `error` 产生式让 Bison 能报告**多个**语法错误。**最终采用的集合（四处，其中三处带
同步符、一处不带）**：

```bison
Stmt   : ... | error SEMI      /* 语句层 */
CompSt : ... | error RC        /* 块层兜底 */
ExtDef : ... | error SEMI      /* 顶层 */
Def    : ... | error           /* 定义层 —— **不带同步符**，见下 */
```

> ⚠️ **`Def : error` 这条是后续追加的，且"不带同步符"是实测选出来的，不是推演。**
> 机理见本节末的「定义层出口 `Def : error`」小节。带同步符的三个出口与它不冲突：
> 它们各自只管一层，`error` 的"丢弃"行为只发生在缺同步符会**少报**的那一层。

> ⚠️ **本节的原始推演已被实测推翻，以下为更正后的内容。** 原稿曾设想的第三条出口是
> `Exp : error RB`，且论证它能就地恢复样例 2 的 `a[5,3]`。**实测加入它反而报出 3 条
> 错误**（行 5、行 5、行 6），直接违反要求书 2.1.3「同一行中不出现多个错误」。
> 故**最终不采用**（机理见下文），真正落地的第三条出口是**顶层**的
> `ExtDef : error SEMI`。

#### 顶层出口 `ExtDef : error SEMI` —— 曾被误判为"要付冲突代价"

本节此前写着：**"要连带修复需要给 `ExtDef` 层加 `error` 出口，实测会引入新冲突
（冲突数必须保持 1，见 §6.2.1），代价大于收益，故明确保留。"** 并据此把"顶层错误
中止后续分析"写进了已知限制。

**这个说法是错的 —— 它不是取舍，是本可免费修好的东西。** 实测两个 Bison 版本
（下表前两行是 `Def : error` **落地前**的数据，后两行是**当前**文法的复测；
bison 3.8.2 与 3.0.4 下**四行的数字都相同**）：

| 文法 | 冲突 state 数 | 悬空 else 所在 state | 总 state 数 |
|---|---|---|---|
| 无 `ExtDef : error SEMI`（旧文法） | 1 | 111 | — |
| 有 `ExtDef : error SEMI`（旧文法） | **1** | **113** | — |
| 无 `ExtDef : error SEMI`（**当前**文法） | **3** | **112** | 116 |
| 有 `ExtDef : error SEMI`（**当前**文法） | **3** | **114** | 118 |

加上它之后冲突 state 的**数**一个没多、内容都是那处悬空 else（当前文法下即
`State 114` = `Stmt: IF LP Exp RP Stmt •` vs `| IF LP Exp RP Stmt • ELSE Stmt`）；
**编号后移只是因为多了一条产生式、多出两个 new state，不是多了一个冲突**。冲突数
哨兵（§6.2.1）不受影响 —— 期望值 1 或 3 的差别来自 `Def : error`，与本节无关。

**效果（实测，`Test/err/toplevel_resync.cmm`）**：

```
输入：第 1 行 int a = 1;     ← 顶层初始化，语法错误
      第 2 行 int b = 2      ← 缺分号，语法错误
修复前：Error type B at Line 1: Syntax error.                    （只报一条，第 2 行被中止吞掉）
修复后：Error type B at Line 1: Syntax error.
        Error type B at Line 2: Syntax error.
```

要求书 2.1.3 要求"报告全部错误"，而修复前的行为是**少报**：`int a = 1;` 换行
`int b = 2` 只报第一处。

#### 为什么 `Exp : error RB` 有害（实测机理）

`bison -t` + yydebug 轨迹显示：

1. `Exp LB . Exp RB` 的**闭包里就含** `Exp → . error RB`，所以 Bison 在下标**内部**就
   找到了能移进 `error` 的状态，**停止弹栈** —— 弹栈并没有越过下标。
2. 随后 `error` 规则的同步符 `RB` **恰好就是外层 `[` 正等待的那个 `]`**，被这个内层
   错误规则吃掉。
3. 外层 `[` 从此永远等不到闭合，语句余下的 `= 1.5;` 全部崩塌 → 同一行冒出第二条错误。

**教训**：设计 `error` 同步点时，不能只看"error 后想跟什么"，还要看**该出口是否已在
当前状态的闭包里**——闭包里有出口时会就地停下，不会按预期往外弹。

去掉它之后，下标内的错误由 `Stmt` 层出口接管（弹到 `Stmt → . error SEMI` 可移进处，
丢弃整条语句后在 `;` 同步）。行 5 恰好 1 条，行 6 由 `IF … Stmt . ELSE` 处暴露，1 条
——与要求书样例 2 完全一致。

#### 各条产生式分别对应的实测结果

（`Stmt` / `ExtDef` / `CompSt` 三条见下；第四条 `Def : error` 见再下面的专节。）

- `Stmt → error SEMI`：样例 2 行 6 `if (…) i = 1 else i = 0;` —— 弹到
  `IF LP Exp RP . Stmt` 后移进 `error`，在行尾 `;` 同步，**恰好报 1 条**；
  样例 6 嵌套注释 —— 第 8 行残留的 `*/` 报 1 条并吞掉第 9 行，**这里只报 1 条才是
  正确的**，多报第 9 行的错反而与样例不符。
- `ExtDef → error SEMI`：顶层。详见上文小节，固定它的用例是
  `Test/err/toplevel_resync.cmm`（实测：删掉本产生式后立刻变红）。
- `CompSt → error RC`：块层兜底，在 `}` 处同步。**理由在闭包层面，不在"附近有没有
  `;`"。**

  `CompSt : LC • DefList StmtList RC` 的闭包里**没有** `Stmt : • error SEMI`：
  `StmtList` 排在 `DefList` **之后**，点在 `DefList` 之前时闭包只展开 `DefList`
  一侧（实测 `syntax.output` 里该状态连 `error` 之外的 Stmt 起始符都是靠
  `DefList → ε` 归约让路的）。

  > ⚠️ **追记（`Def : error` 落地后，本小节的实测证据已过期，必须重读）。**
  > 加入 `Def : error` 之后，State 26 的闭包里**多出了 `Def : • error`**，该状态
  > 现在是这样（当前 `syntax.output` 逐字粘录）：
  >
  > ```
  > State 26
  >
  >    32 CompSt: LC • DefList StmtList RC

  是后来专门构造出来的）。**本轮仍不删**，但请注意上面的追记：**这两类输入的判别力
  已被 `Def : error` 吸收，当前 28 组差分组输入下删除它也 0 差异、冲突数不变**。
  所以现在的保留理由从"有实测证据证明它不可删"变成了"**不留白删、留着当保险**"。**不要
  拿本段旧数据当作它仍有贡献的证据。**

#### 定义层出口 `Def : error`（**不带同步符**）—— 后续追加，纯收益

**要修的问题**：块内局部定义缺分号时，`CompSt : LC • DefList StmtList RC` 的闭包里
**没有** `error` 出口（理由见上文 `CompSt → error RC` 小节：`StmtList` 排在 `DefList`
之后），Bison 只能弹到函数末尾的 `}`，于是**同一块内后续错误全被丢弃**。

**关键结论：带不带同步符，行为完全不同 —— 而不带同步符不额外付冲突代价。**

| 写法 | 冲突 state | 场景①：`int main()\n{\n  int a\n  int b;\n  a = 1\n  b = 2;\n}\n` | 场景②：`int main(){ int a } int f(){ int b }`（单行） |
|---|---|---|---|
| 不加 | 1 | 只报 1 条（`B4`，少报） | 报 2 条（`B1, B1`） |
| `Def : error SEMI` | 3 | 报 2 条（`B4, B6`） | **只报 1 条**（`B1`，少报） |
| `Def : error RC` | 3 | **只报 1 条**（`B4`，少报） | 报 2 条（`B1, B1`） |
| **`Def : error`（裸）→ 采纳** | **3** | **报 2 条（`B4, B6`）** | **报 2 条（`B1, B1`）** |

**机理**：带同步符时 Bison 先**丢弃**词法单元直到同步符出现才归约。场景②整份文件里
一个 `;` 都没有，`SEMI` 版本只能丢到 EOF；场景①里 `RC` 版本则把 `}` 本身当作同步符
吃掉。裸 `error` 移进后**立即归约、不丢弃任何前瞻**，两个场景都对。

**为什么是纯收益**：上表里"不加"的冲突数是 1，三种加法的冲突数都是 3 —— `error SEMI`
与裸 `error` 引入的是**同样的两个** state（`CompSt: LC • DefList StmtList RC` 与
`DefList: Def • DefList`）。冲突由 `error` 这个**符号本身**引起（`DefList` 可空，
"移进 `error`"与"按 `DefList → ε` 归约"不可兼得），与后面跟不跟同步符**无关**。
故"去掉同步符"没有代价 —— 本文档此前把 `Def : error SEMI` 记为"代价大于收益"，
**代价那一半是误判**（真实代价只有冲突数 1 → 3，与同步符无关）；而"收益"那一半在
**多行错误样例**（评分包含）下是必需的。两处修正合起来，结论从"否决"翻转为"采纳"。

**守护用例**：`Test/err/def_resync.cmm`（输入即场景①，`.exp` 为两行 `B4`/`B6`）。
实测删掉本产生式后该用例立刻变红，加回即绿。

#### 已试并否决的备选（实测数据）

| 备选 | 冲突数变化 | 结论 |
|---|---|---|
| `Exp : error RB` | 1 → 1 | **否决**：不报错但语义有害，同一行报出 2 条错误，违反 2.1.3 |
| 裸 `Exp : error` | 1 → 2 | 否决：引入新冲突且无必要 |
| `ExtDef : error SEMI` | 1 → 1 | **采纳**（本文档此前误记为 1 → 增加，实测两版 Bison 均仍为 1，见上文小节） |
| `Def : error SEMI` | 1 → 3 | **否决**：冲突数变化与裸式**相同**，但它**会少报**（见上表场景②）。否决理由是"少报"，**不再是"冲突代价"** |
| `Def : error RC` | 1 → 3 | **否决**：同上，**会少报**（见上表场景①），否决理由同样是"少报" |
| **裸 `Def : error`** | 1 → 3 | **采纳**（见上一小节）：同一冲突代价，但两个场景都对 |

#### 已知限制（明知的取舍，非静默缺陷）

**一、顶层错误：文法层已经修好；`src/main.c` 的抽干循环因此成了"不可达的安全网"。**

修复前的症状：顶层（`ExtDef` 层）无处移进 `error`，Bison 只能弹空栈并**中止**分析，
而中止意味着**再也不会调用 `yylex`**，所以文件剩余部分的**词法**错误会整片丢失。
当时分两步修：先在 `src/main.c` 里加一个"抽干循环"（`yyparse()` 返回后若
`hasError()`，继续调 `yylex()` 到返回 0），**现在又补上了真正的文法出口
`ExtDef : error SEMI`（见上文，代价为零）**。

输入 `/tmp/fx/i2_a.cmm` = `int a = 1;` 换行 `int b = ~2;`，三种配置的**完整实测输出**：

```
① 改动前（无 ExtDef 出口、无抽干）
Error type B at Line 1: Syntax error.

② 改动前（无 ExtDef 出口、有抽干循环）
Error type B at Line 1: Syntax error.
Error type A at Line 2: Mysterious character "~".

③ 改动后（有 ExtDef : error SEMI）
Error type B at Line 1: Syntax error.
Error type B at Line 2: Syntax error.      ← 新报出的"真实语法错误"（顶层初始化不合法）
Error type A at Line 2: Mysterious character "~".
```

①→② 是当初抽干循环的贡献（`~` 从"从未被扫到"变成"被报出"）；②→③ 是顶层出口的贡献
（第 2 行本身是错的，不再被中止吞掉）。

**代价（实测，如实记录）**：加上 `ExtDef : error SEMI` 之后，Bison 在顶层永远能找到
可移进 `error` 的状态，唯一的 `YYABORT` 只会在 **EOF** 时触发 —— 也就是说**整份输入
一定已被 `yylex` 扫完**。于是 `src/main.c` 里那个抽干循环再也取不到任何词法单元：

```
$ 差分：把 main.c 的抽干循环改成 `if (0)` 后逐用例对拍
  有抽干 vs 无抽干：30 个用例输出完全相同，0 个不同
```

（本行原为 "29 个用例、0 个不同"，是在加入 `Def : error` 与 `Test/err/def_resync.cmm`
**之后重测过的** —— 新增的恢复出口没有让抽干循环重新变得可达。）

即它已从"必要的补丁"退化为**安全网**（保留它，是为了不让"顶层恢复能力"成为唯一
防线；它对本项目的输出已无影响）。固定"顶层错误之后词法错误一条不少"的用例仍是
`Test/err/drain_after_toplevel.cmm`，但它现在钉住的是**整条流水线的结果**，而不是
抽干循环本身 —— 这一点必须说清楚，否则会误以为那条用例在守护 `main.c` 的循环。

仍然中止的输入**长什么样**（该用例就是照此构造的）：**出错点之后一个 `;` 都没有**，
`ExtDef : error SEMI` 永远等不到同步符，Bison 只能丢弃到 EOF 再中止
（实测 `yyparse()` 返回 1）。若错误点之后有 `;`，恢复就能完成，分析会正常走完。


**二、局部变量定义处缺分号时一个语句块内只能报出第一处 —— 已修复，保留记录备查。**

> ⚠️ **本条已不再是限制。** 修法是给 `Def` 补一个**不带同步符**的出口
> `Def : error`（详见上文「定义层出口 `Def : error`」小节）。此处保留修复前的实测
> 记录与**修复后**的对照，以便复现与防止回退。

**修复前的症状**：

```
int main() {
    int a          ← 缺分号
    int b;         ← 这一行不会被报错
    a = 1          ← 缺分号
    b = 2;         ← 这一行也不会被报错
}
```

实测**只报行 3**（行号取的是**触发错误的那个先行词法单元** `int`（行 3）所在行，
而不是"缺分号的那一行"行 2）：

```
$ ./parser /tmp/doc/b.cmm        # 输入即上方代码块
Error type B at Line 3: Syntax error.          ← 修复前：只 1 条
```

原因：缺分号的是 **Def 层**错误，而 `CompSt → LC . DefList StmtList RC` 状态的闭包里
**没有** `error` 出口（`StmtList` 在 `DefList` **之后**，不在其闭包中），Bison 只能一路
弹到 `ExtDef → Specifier FunDec . CompSt`，在函数末尾的 `}` 处同步 —— **块内**后续错误
全部被丢弃。

**修复后（实测，同一份输入）**：

```
$ ./parser /tmp/doc/b.cmm
Error type B at Line 3: Syntax error.
Error type B at Line 5: Syntax error.          ← 修复后：2 条，块内后续错误不再丢
```

**仓库里的固定用例是 `Test/err/def_resync.cmm`**（排版略有不同：`{` 独占一行，故触发点
整体后移一行，`.exp` 为 `Line 4` / `Line 6`）：

```
1  int main()          3    int a      ← 缺分号（触发点是下一行的 int，行 4）
2  {                   4    int b;     ← 该行不会被报错
3    int a             5    a = 1      ← 缺分号（触发点是下一行，行 6）
4    int b;            6    b = 2;     ← 也不会被报错
5    a = 1             7  }
6    b = 2;
7  }
```

两处口径完全一致 —— 都是**触发错误的那个先行词法单元**所在行。**不要把行号直接抄到
别的排版上**：同一份错误在不同排版下报出的行号本就不同。

**代价与取舍（已按实测更新）**：冲突数 1 → 3。**但这不是"为覆盖率付冲突代价"** ——
那 2 处新增冲突由 `error` 符号本身引起，**带同步符的 `Def : error SEMI` 有完全相同的
代价**（见上文对照表）。所以真实取舍只是"要不要这个出口"，而评分包含多行错误样例，
**要**。哨兵（§6.2.1、`scripts/run_tests.sh`）的**灵敏度不变**（冲突数一变就报警），
只是期望值由 1 改为 3。

**限制的边界（修复前实测，仍然成立）**：同步点是函数末尾的 `}`，所以丢弃只发生在
**该函数体内部**；`}` 之后的兄弟定义仍会被正常解析和检查。两个函数各缺一处分号时
两处都会被报出：

```
$ ./parser /tmp/doc/c.cmm
Error type B at Line 4: Syntax error.
Error type B at Line 9: Syntax error.
```

**回退检测**：删掉 `Def : error` 后 `Test/err/def_resync.cmm` 立刻变红
（实测：`.exp` 少一行，且 `run_tests.sh` 的冲突数断言同时报 1 ≠ 3）。

**三、同一行上、跟在本条 type A 之后报出的 type B 会被抑制 —— 这可能吞掉一条真实的
语法错误。**

抑制的实现在 `src/report.c`：记住最近一次 type A 的行号 `lastALine`，收到 `'B'` 且行号
相同时**只置 `errorFlag`、不打印**（理由见 §7.4(1)：官方选做样例 2/4 的期望输出只含
type A 行、不含 type B）。

**这个判据是按"已报告过的行号"做的近似，不是因果判断**，所以它也会误伤。反例
（**该输入不满足要求书"同一行不出现多个错误"的前提**，属于明知的代价）：

```
1  int main()
2  {
3    int a = 1        ← 缺分号：真实的语法错误
4    ~ }              ← 未定义字符 ~ ：type A
5  }
```

实测（差分：把抑制关掉做对照）：

```
有抑制（当前实现）：
    Error type A at Line 4: Mysterious character "~".
无抑制（对照）：
    Error type A at Line 4: Mysterious character "~".
    Error type B at Line 4: Syntax error.        ← 缺分号的那条真实错误
```

第 4 行的 `}` 才让分析器发现第 3 行缺分号，而这条 `B4` 与 `A4` 同行且排在 A 之后，
于是被抑制吞掉。**结论：在满足要求书前提的输入下，本程序仍可能少报一条同行的
type B。** 这是"按行号近似"的固有代价，不是可以靠改判据消除的 bug（改成"因果判断"
需要回溯 Bison 的内部状态，代价远大于收益）。

补一个**顺序相关**的旁证：判据取决于"谁先报出"，而不是"谁由谁引起"。下面的输入里
`B` 在 `A` **之前**报出（缺分号在 `int` 处就被检出，早于 `09` 被扫描），`lastALine`
尚未置位，于是**两条都会打印**：

```
输入：int main() { int i = 1      ← 缺分号
                   int j = 09; }  ← 非法八进制
实测：Error type B at Line 4: Syntax error.
      Error type A at Line 4: Illegal octal number '09'.
```

**这份清单以实测为准，不以推理为准。** 实现后跑全套样例，按失败用例增删同步点，并以
`bison -v` 生成的 `syntax.output` 检查新增冲突。

### 6.4 Bison 版本兼容

- 用 `%define api.value.type {Node *}` 而非 `%union`
- **不使用** `%define parse.error detailed`（Bison 3.0.4 不支持该值）
- 错误信息在 `yyerror` 中自行拼装，不依赖 Bison 的错误文本
- **已在 bison 3.0.4 实机复跑**（此前这里写"无法实机验证"，不成立）：整套 30 个用例
  全过、冲突数同样恰好 3、冲突 state 编号也与 3.8.2 一致。做法与实测表见 §2.2。

## 7. 输出规范

### 7.1 有词法或语法错误时

**只**输出错误信息，**绝不**输出语法树。格式：

```
Error type A at Line 4: Mysterious character "~".
```

- 错误类型只能是 `A` 或 `B`
- 每条错误单独占一行
- 必须报告**全部**错误（同一行保证不出现多个错误）
- 说明文字内容不限，但**错误类型和行号必须正确**

### 7.2 无错误时

先序打印语法树，规则见 §4.2。

### 7.3 两种模式互斥的实现

用一个全局 `errorOccurred` 标志：`yyerror` 与词法错误处理函数置位。`main` 在
`yyparse()` 返回后检查该标志——置位则什么都不打印（错误已在过程中逐条输出），
未置位才调用 `printTree`。

### 7.4 错误报告的四处修正（整分支最终审查，实测）

> **标题原先写"三处"却列了四条。** 四条里 **(1)(2)(3) 是错误报告类**（抑制同行噪声、
> 抽干剩余输入、修正未闭合注释的行号），**(4) 是数值输出类** —— `FLOAT` 缓冲区截断
> 只改变打印出来的数值，与错误类型/行号无关。两者不是同一类问题，故标题改为"四处"，
> 并把类别点明。

以下四处在开发期被漏掉，均由整分支审查发现。**共同的根因是：四条修正的行为都在
`parser` 的端到端输出里，但当时的用例集没有覆盖到它们**——非法数字只被词法单测
（`Test/unit/test_lexer` 直接调 `yylex()`）覆盖，看不见语法层的下游噪声；顶层中止、
未闭合注释的行号、大浮点数的数值则完全没有用例。现已各补端到端用例。

#### (1) 同行的 type B 必须抑制（判据是按行号近似，**不是**因果判断）

数字规则（`0[xX]{ALNUM}+` / `0{DIGIT}+` / `{FBASE}[eE][+-]?`）发现非法数字后**只报
type A、不返回词法单元**，语法分析器于是看到 `int i = ;`，在同一行再报一条 type B。

修复在 `src/report.c`：记住最近一次 type A 的行号 `lastALine`，`reportError` 收到
`'B'` 且行号与之相同时**只置 `errorFlag`、不打印**。**只在同一行**抑制，A 在行 N、
B 在行 N+1 时不受影响。

> ⚠️ **这里原先写"同行的 B 必然是 A 的下游噪声，故可以安全抑制"——这句话是错的，
> 已删除。** 抑制的判据是**按"已报告过的行号"做的近似**，不是因果判断，因此它也会
> 吞掉**真实、独立的语法错误**（反例与实测见 §6.3 已知限制三）。
>
> **抑制之所以必要，不是因为"B 必然是噪声"，而是因为官方选做样例 2 / 样例 4 的期望
> 输出只含 type A 行、不含 type B。** 不复现这两条样例就无法通过判分，所以这是一处
> **为了对齐官方输出而付出的、明知的代价**，不是一处"因为推理成立所以安全"的优化。
> 官方样例如下（期望输出里没有任何 type B）：


```
$ ./parser Test/sample/illegal_oct.cmm      # 官方选做样例 2
Error type A at Line 3: Illegal octal number '09'.
Error type A at Line 4: Illegal hexadecimal number '0x3G'.

$ ./parser Test/sample/illegal_exp.cmm      # 官方选做样例 4
Error type A at Line 3: Illegal floating point number "1.05e".
```

> **说明文字与官方 PDF 的关系**：PDF 选做样例 2 用的是**单引号**（`'09'` / `'0x3G'`），
> 选做样例 4 与必做样例 1 用的是**双引号**（`"1.05e"` / `"~"`）。本实现按 PDF 逐字对齐，
> 故这两条用单引号、其余用双引号。要求书 2.1.3 明说"说明文字的内容没有具体要求"，
> 只有**错误类型和行号**参与评分。

#### (2) 顶层语法错误会让文件剩余部分的**词法**错误整片丢失

见 §6.3 已知限制一。这里先后有两层修法：

1. **`src/main.c` 的抽干循环**（`yyparse()` 返回后把 `yylex()` 抽干到返回 0）。当时的
   决策是"不动文法"，因为误以为顶层加 `error` 出口会增加冲突；
2. **`ExtDef : error SEMI`**（文法出口本身）。实测冲突**数不变**（旧文法 1 → 1，当前
   文法 3 → 3，两版 Bison 一致，见 §6.3 的表），代价为零，故已采纳 —— 这一层是治本的。

以 `int a = 1;` 换行 `int b = ~2;` 为例，三种配置的**完整实测输出**（同样三份，逐字）
见 §6.3 已知限制一的代码块：无出口无抽干 → 只有 `B1`；无出口有抽干 → `B1, A2`；
有顶层出口 → `B1, B2, A2`。中间那份正是当初抽干循环的贡献，最后那份是顶层出口的
贡献（`B2` 是第 2 行本身的语法错误，不再被中止吞掉）。

**副作用（已实测，见 §6.3 已知限制一）**：顶层不再中止之后，`main.c` 的抽干循环再也
取不到任何词法单元 —— 把全部用例在"有抽干 / 无抽干"两个二进制上对拍，输出**逐字节
完全相同**（30 个用例、0 个不同，见 §6.3 已知限制一的实测块）。它从此是**安全网**，不再是被用例守护的补丁；这一点
必须写明，否则会误以为 `Test/err/drain_after_toplevel.cmm` 在守护 `main.c` 那个循环。

**该用例如今钉住的是另一件事**：顶层错误之后**一个 `;` 都没有**时分析**仍然中止**
（实测 `yyparse()` 返回 1），且文件剩余部分的词法错误一条都不少。若错误点之后有 `;`，
`ExtDef : error SEMI` 能完成同步、分析正常走完（这由
`Test/err/toplevel_resync.cmm` 钉住）。

#### (3) 未闭合注释处的 type B 曾倒指回合法代码

`<COMMENT><<EOF>>` 的动作原本在 `return 0` 前没有更新 `curTokenLine`，它仍停在最后
一个真实词法单元上，于是这条 B 指到了**上一行完全合法的代码**。修复：`return 0` 前
加 `curTokenLine = yylineno;`，让这条 B 指向 EOF。

```
$ ./parser Test/err/unterm_inbody.cmm       # 注释在函数体内
Error type A at Line 4: Unterminated comment.
Error type B at Line 5: Syntax error.       # 修复前是 "at Line 3"（那行是 int a;，合法）
```

#### (4) `FLOAT` 值在 63 字符处被静默截断

数字的词素转十进制缓冲区原为 `char buf[64]`，而 `%f` 把 `0.5e103`（附录 A 列出的
合法形式）展开成 **110** 个字符（103 位整数 + `.` + 6 位小数），于是打出一个被截断的
**错值**。已把缓冲区统一改为 `NUMBUF`（512）。`%f` 不写越界，只是结果错，故原缺陷
没有 UB、也没有崩栈之类的旁证，只能靠比对数值本身发现。

```
$ ./parser /tmp/fx/i4.cmm | grep FLOAT
                  FLOAT: 5000000000000000009578375428673343681079775636325960055764017572996896621019943779806180725540901617664.000000
```

与 `python3 -c 'print("%.6f" % 0.5e103)'` 的输出**逐字相同**。

**为什么 512 是"可证明充分"而不是"碰巧够用"**：缓冲区要装的量是"**任意 `double` 的
`%f` 全量展开**"。`%f`（6 位小数）能产生的最长结果出现在 `DBL_MAX`，实测 316 字符：

```
$ python3 -c 'import sys; s = "%f" % sys.float_info.max; print(len(s))'
316
$ python3 -c 'import sys; print("%f" % sys.float_info.max)'
179769313486231570814527423731704356798070567525844996598917476803157260780028538760589558632766878171540458953514382464234321326889464182768467546703537516986049910576551282076245490090389328944075868508455133942304583236903222948165808559332123348274797826204144723168738177180919299881250404026184124858368.000000
```

故 **512 > 316 + 1（`\0`）**，对任何 `double` 都不会截断；`strtol` 那条路径更短
（`long` 的十进制最多 20 位）。这不是凭感觉挑的大数。

**守护它的用例：`Test/sample/floatbuf.cmm`**（`float i = 0.5e103;`，展开 110 字符）。
`.exp` 里的数值由 `python3 -c 'print("%f" % 0.5e103)'` **独立算出**，不是从程序输出
反填。变异测试（把 `NUMBUF` 改回 64）：

```
NUMBUF=64   FLOAT: 500000000000000000957837542867334368107977563632596005576401757
            ↑ 只有 63 个字符（下面这行是完整真值，便于逐字对比），用例**变红**
            FLOAT: 5000000000000000009578375428673343681079775636325960055764017572996896621019943779806180725540901617664.000000
NUMBUF=512  输出与 .exp 逐字节一致，用例变绿
```

**这条修复此前是全提交唯一没有任何用例守护的改动**（把 `NUMBUF` 改回 64 仍然全绿），
现在由 `Test/sample/floatbuf.cmm` + 上面这组变异测试钉住。

## 9. 测试策略

**唯一验收标准：`Test/sample/` 下的期望输出必须与程序实际输出逐字节一致**——空格、
缩进、行号都不能差。

### 9.1 用例来源

1. **要求书样例**（必做 4 个 + 选做 6 个）：输入从 PDF 逐字抄录，期望输出**同样逐字
   手抄**，不从程序输出反填——否则测试就退化成"验证程序等于它自己"。
2. **自建边界用例**（`Test/err/`），针对本设计识别出的风险点：
   - 多行注释跨换行后的报错行号（§5.6 点名的最高风险项）
   - `0x3F`（等长规则顺序依赖）、`00`、`08`、`0x`
   - `1.05e+`、`.5E03`、`43.e-4`（附录 A 补充说明里给的合法指数形式）
   - 一个文件内多个错误、跨多行的多个错误
   - 空文件、只有注释的文件
   - **顶层错误之后一个 `;` 都没有 ⇒ 仍然中止**（`Test/err/drain_after_toplevel.cmm`；
     钉住"中止之后文件剩余部分的词法错误一条不少"。**它不再守护 `main.c` 的抽干循环
     —— 见 §6.3 已知限制一 / §7.4(2)：`ExtDef : error SEMI` 落地后那个循环已取不到
     任何词法单元**，用例钉的是整条流水线的结果）
   - **顶层错误的就地复原**（`Test/err/toplevel_resync.cmm`；钉住 `ExtDef : error SEMI`
     —— 顶层出错后在 `;` 处同步，后续顶层错误仍报得出来。删掉该产生式此用例立刻变红）
   - **函数体内未闭合注释**（`Test/err/unterm_inbody.cmm`；钉住 §7.4(3) 的 B 行号）
   - **块层 `error RC` 复位**（`Test/err/block_resync.cmm`；钉住 §6.3 的 `CompSt : error RC`）
   - **定义层 `error` 复位**（`Test/err/def_resync.cmm`；钉住 §6.3 的 `Def : error`
     —— 块内局部定义缺分号后，同块**后续**错误仍报得出来。删掉该产生式此用例立刻
     变红：实测 `.exp` 少一行，且冲突数断言同时报 1 ≠ 3。它是"**不带同步符**"这一
     选择的守护用例：换成 `Def : error SEMI` 或 `error RC` 都会让它变红）
3. **要求书样例的端到端副本**（`Test/sample/illegal_oct.cmm`、`illegal_exp.cmm`）：
   选做样例 2 / 样例 4 此前只被**词法单测**覆盖（直接调 `yylex()`，看不见语法层），
   于是"非法数字连报一条同行 type B"的缺陷潜伏至今。这两个用例走完整 `parser`，
   期望输出逐字取自 PDF（见 §7.4(1)）。
4. **关键实现的守护用例（放在 `Test/sample/`，不是"要求书样例"）**：
   `Test/sample/floatbuf.cmm` 钉住 §7.4(4) 的 `NUMBUF` —— 它此前**没有任何用例守护**
   （把 `NUMBUF` 改回 64 仍然全绿），现在只有这个用例能发现它被改小。见 §7.4(4) 的
   变异测试。

> **第 1 条"绝不从程序输出反填"的例外，如实说明**：第 2、4 条里的自建用例
> （`drain_after_toplevel`、`toplevel_resync`、`unterm_inbody`、`block_resync`、
> `def_resync`、`floatbuf`）**必然是反填的** —— 它们本来就是要固定"当前实现的行为"，
> 不存在可抄的官方期望。为不让反填变成"验证程序等于它自己"，这些用例**各自做了独立
> 交叉验证**：
> - `floatbuf` 的数值用 `python3 -c 'print("%f" % 0.5e103)'` **独立算出**，与程序输出
>   逐字比对（不是抄程序输出）；`floatbuf.exp` 的结构部分抄自 `expfloat.exp`（那是
>   要求书样例的手抄副本）；
> - `drain_after_toplevel` / `toplevel_resync` / `block_resync` / `def_resync` 都用
>   **变异测试**证明判别力：删掉被守护的那条产生式（或把 `NUMBUF` 改小），用例必须
>   变红（§6.3、§7.4、§9.2 各给出了实测 diff）；
> - `unterm_inbody` 的行号口径与要求书对"行号 = 第一个词素出现的行"的定义一致，且
>   它的判别力来自"删掉 `curTokenLine = yylineno` 后 B 会倒指回第 3 行"（§7.4(3)）。
>
> **另注（`unterm_inbody.cmm` 对结尾换行敏感，故该文件内没有加注释）**：该用例依赖
> `curTokenLine = yylineno` 在 EOF 处的取值 —— 文件**有**结尾换行时 EOF 落在第 5 行
> （`curTokenLine = 5 ≠ commentStart = 4`），B 会打印；若把结尾换行删掉，两者都是 4，
> B 会被 §7.4(1) 的同行抑制吞掉，用例含义随之改变。**这个文件的结尾换行不能删。**
> 也正因为该用例的行号是**被断言的输出**（第 4/5 行），在它内部加注释行会整体移动
> 行号、把"注释"和"被断言的内容"搅在一起，故说明写在这里，不写进 `.cmm`。
>
> **`Test/` 下 `.cmm` 的原则是"纯输入、不带说明性注释"，只有两处例外**：
> `drain_after_toplevel.cmm` 与 `toplevel_resync.cmm` —— 它们的成立条件（"出错点之后
> 一个 `;` 都没有，所以仍然中止" / "顶层在 `;` 处就地复原"）不写在文件里就会读不懂。
> 这两处的说明写在**文件末尾**的 `//` 注释里，而不是开头：**末尾注释不改变上面几行的
> 行号**，所以改注释不会让 `.exp` 失效（写成开头注释的话，注释行数就成了被断言的
> 行号的一部分 —— 实测踩过：注释由 5 行改成 6 行，`.exp` 立刻变红）。
> **`unterm_inbody.cmm` 属于"会影响用例"的那一类**（它断言的正是第 4/5 行），所以
> 连末尾注释也不加，说明只写在本文档。

### 9.2 执行

`scripts/run_tests.sh`：遍历 `Test/sample/*.cmm` 与 `Test/err/*.cmm`（`Test/unit/` 由
`unit-test` / `lexer-test` 各自负责），比对同名 `.exp`，输出 diff 与汇总。
全部用例在 WSL 中运行。

**当前共 30 个用例**，预期以「通过 30 个，失败 0 个」结尾（要求在 bison 3.8.2 与
3.0.4 下各复跑一次，两次都是 30/30；见 §2.2）。**新增用例时必须同步更新这个数字** ——
README 与本文档都写着它，`run_tests.sh` 也会在"一个用例都没跑"时报 FAIL。

> 调用方式：**直接 `bash scripts/run_tests.sh`**（需先 `make`）。Makefile 里**没有**
> `test` 目标 —— 评分流程是 `make` + `./parser <文件>`，不需要测试入口；而把
> `test` 挂在开发期目录 `scripts/` 上，等于让"构建可用性"取决于该目录是否随提交
> 一起打包。`make` 必须能独立跑通，故测试入口只写进文档。

脚本除了比对 stdout，还断言两件"比对本身看不见"的事：

- **stderr 必须为空**。此前用 `> "$tmp" 2>&1`，把错误信息改成写 stderr 仍然全绿，
  而要求书 2.1.3 要求输出到**标准输出**（判分脚本读 stdout）。现已改为 stdout 与
  stderr 分别重定向，stderr 非空即判 FAIL。
- **`syntax.output` 里恰好 3 个冲突 state 且每个都是 `1 shift/reduce`**（悬空 else 1 +
  `Def : error` 引起的 2，归属见 §6.2.1 / §6.3）。这条哨兵不可省：实测有无
  `%left LB DOT` 的 LR 动作表**完全相同**，全部 `.exp` 比对都察觉不到它被误删，只有
  冲突计数能发现。**期望值由 1 改为 3 不改变哨兵语义**（冲突数一变就报警，不区分
  "变好"还是"变坏"）。

## 10. 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 多行注释导致 `yylineno` 漏计 | 报错行号错误 → 直接失分 | §5.6：`yylineno` 由 flex 自动维护，**禁止**在 action 里手工 `+=`（会重复计数）；未闭合注释另存 `commentStart` 取其起始行 + 专项用例 `Test/err/unterm.cmm` |
| 十六进制校验模式误写成 `{LETTER}+` | `0x3G` 检测不到，静默漏报 | §5.3 已写明必须用 `({LETTER}\|{DIGIT})+` + 专项用例 |
| `error` 产生式引入**清单外**的新冲突 | 可能改变正常语句的解析 | `bison -v` 检查 `syntax.output`，与 §6.2.1 清单比对；`run_tests.sh` 断言冲突 state **恰好 3 个**且每个为 `1 shift/reduce`（State 26 / 31 / 114） |
| Bison 3.8.2 与评分环境 3.0.4 的行为差异 | 评分机上编译失败 | 只用两版通用的写法（§6.4），**并已在 3.0.4 实机复跑 30/30**（§2.2） |
| 样例期望输出为手工抄录 | 抄错会导致"程序正确却测试失败" | 抄录后与 PDF 二次核对；自建用例的反填例外与交叉验证见 §9.1 |
| `printTree` 误判结点类型 | 输出格式整体错乱 | §4 显式 `kind` 字段，不靠推测 |
| 用 `make -j` 构建 | 并发跑两次 bison 写同一个 `syntax.tab.c` | Makefile 里已写明不要用 `-j`；评分镜像的 make 4.2 不支持 `&:`（§8） |
| 同行 type B 抑制误伤真实错误 | 少报一条 type B（符合要求书前提的输入下也可能） | §6.3 已知限制三：明知的代价，反例与顺序相关性均已实测记录 |
