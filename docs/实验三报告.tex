\hline
表达式与条件 & 表达式翻译以 \code{place} 为\textbf{继承属性}（见亮点 1）；条件翻译以真、假两个目标标号为继承属性，按短路方式生成跳转，\textbf{不回填}。括号不产生任何 IR。\\
\hline
语句与函数 & 按指导书表 3 生成 \code{IF}/\code{WHILE}/\code{RETURN} 等模板；函数依次发 \code{FUNCTION}、\code{PARAM}、函数体。\textbf{实参 \code{ARG} 与形参 \code{PARAM} 顺序相反}：虚拟机中 \code{ARG} 压栈、\code{PARAM} 弹栈，故 \code{ARG} 必须按源码逆序发。\\

\section*{二、如何编译}

\begin{lstlisting}[language=bash]
# Ubuntu 22.04 / WSL
sudo apt-get install -y flex bison gcc make
make                         # 生成 ./parser（./cc 内容相同）
./parser in.cmm out.ir       # 写文件
./parser in.cmm              # 写 stdout

\section*{三、亮点 1：\code{place} 作为继承属性——把结果直接算进目标变量}

最自然的写法是让表达式翻译\textbf{自造临时变量}：每个子表达式把值算进一个新临时变量，
再由调用方把它拷到真正需要的地方。这样语义上完全正确，但会稳定多出纯拷贝。以
\code{n = read();} 和 \code{if (n > 0)} 为例，朴素写法先得到：

\begin{lstlisting}
READ t1          # read() 先读进临时变量
v1 := t1         # 再拷进赋值目标
t2 := #0         # 常量 0 也先物化
IF v1 > t2 GOTO label1
\end{lstlisting}

本实现把“结果算到哪”作为参数一路传下去：\code{translateExp(tail, e, place)}。
赋值语句把左值 \code{v1} 本身作为 \code{place} 传给右子表达式，于是 \code{read()} 直接
写进 \code{v1}；条件翻译遇到简单操作数（\code{EX\_ID} 取变量、\code{EX\_INT} 取立即数）
时直接把它放进 \code{IF}，不再物化常量。同一段源码只需两条指令（下列为示意形态；
经 O9 条件反转后，实际首条条件跳转形如 \code{IF v1 <= \#0 GOTO label2}）：

\begin{lstlisting}
READ v1
IF v1 > #0 GOTO label1
\end{lstlisting}

这不是事后补的窥孔优化，而是\textbf{翻译接口的选择}：\code{place} 是继承属性，
调用方先决定目的地，子表达式直接往里算。收益有两层：其一，赋值、读入、条件比较这些
高频路径天然少一条搬运；其二，后续优化 pass 不必再为这些拷贝做消除。需要说明的是，
要求书 4.1.6 样例 1 的“优化后版本”主要消除的是冗余标号与常量算式，其 IR 仍保留
\code{READ t1} / \code{v1 := t1} 与 \code{t2 := \#0} / \code{IF v1 > t2}；本实现的
\code{place} 继承属性进一步把 read 的结果直接写进目标、把常量直接内联进 \code{IF}——
这是翻译接口带来的额外收益，不是对样例的逐字复刻。\code{place} 传 \code{NULL}
表示“值不被需要”（表达式语句），此时仍照常翻译两侧，因为函数调用等副作用不能丢。

\section*{四、亮点 2：多维下标的地址一次线性化}

链式写法把每个下标的结果物化成“行地址”：先算 \code{\&a[i+1]}，再在行地址上加
\code{j*4}，最后解引用。每多一维就多一条 \code{ADD}，常量下标还会留下可折叠的中间量；
更深的问题是，它把“数组的某一维”当成一个可独立求值的对象，而 C-- 中部分下标得到的
仍是数组，不能当标量用。

本实现按
\begin{center}
\code{\&a + $\sum_d$ (index$_d$ * stride$_d$)}
\end{center}
一次算出元素地址：\code{stride$_d$} 由\textbf{类型链}给出——取完第 $d$ 个下标后剩下的
元素类型的字节数；常量下标直接累加进常数偏移，只有变量下标才发一条 \code{MUL}；
所有项求和后，\textbf{基地址只加一次}。对

\begin{lstlisting}
int a[4][6];
a[i+1][j*2] = 0;
\end{lstlisting}

\code{a} 的类型是 \code{int[4][6]}，取第一个下标后元素类型为 \code{int[6]}，步长
$6\times4=24$；取第二个下标后为 \code{int}，步长 4。生成（示意形态，省略了
index 的搬运）：

\begin{lstlisting}
t1 := i + #1
t2 := t1 * #24
t3 := j * #2
t4 := t3 * #4
t5 := t2 + t4
addr := &a + t5
*addr := #0
\end{lstlisting}

这里没有“行地址”这个中间对象，每个变量下标恰好一条 \code{MUL}，基地址只在最后加一次；
若某个下标是常量，连它的 \code{MUL} 都不发（例如 \code{a[0][i]} 只剩
\code{t := i * \#4} 与 \code{addr := \&a + t}）。

这一步有一个容易漏掉的前提：\textbf{翻译层必须自己保存“源码名 → 类型”表}。语义分析
结束时局部作用域已经弹出，翻译阶段再查符号表拿不到局部数组的类型，也就求不出步长。
数组形参还要在这个表里多记一个标记：形参的运行时值\textbf{已经是基地址}，体内下标必须
用 \code{opVar}（\code{temp + i*4}），不能再取 \code{\&}；调用点则相反，局部数组传
\code{ARG \&arr}，转传数组形参传 \code{ARG v}。两处不对称只要写反一处，就会得到
“地址的地址”，运行结果立即出错。

\section*{五、亮点 3：独立的 IR 与优化；静态条数 $\neq$ 动态条数}

如果边遍历语法树边打印，IR 一产生就写进了输出流，既无法整体优化，也无法统一改输出
格式。本实现先把 IR 建在内存的带哨兵双向循环链表里，再跑优化 pass，最后从唯一的
\code{printIR} 输出。优化器采用\textbf{固定点}框架：反复执行各子 pass，直到一整轮
不再有任何改动（设 20 轮上限，触发即告警）；优化前后都断言临时变量单赋值，防止
某个 pass 把错误放大。

九条规则是：O1 常量折叠、O2 代数化简、O3 立即数内联、O4 结果直达、O5 冗余拷贝消除、
O6 无引用标号删除、O7 删除紧邻目标标号的 \code{GOTO}、O8 \code{GOTO} 链折叠、
O9 条件反转 + fall-through。O3/O4 只对 \code{irTempDefCount == 1} 的临时变量生效：
条件取值模板会两次定义同一个临时变量，若把它当普通常量传播，语义就错了。O5 删除
\code{x := x}；当前覆盖语料中没有自拷贝，故它对下表合计没有额外贡献（数字未变）。

关键在于：\textbf{静态指令条数不等于动态执行条数}。虚拟机的跳转把 IP 写成目标标号
自身的下标，因此被跳转命中的 \code{LABEL}/\code{FUNCTION} 行会被跨过、不计数；只有
控制流\textbf{落入}的标号行才计数。这条计数语义改变了“删一条跳转就省一条指令”的直觉：

\begin{itemize}
\item O7 删掉紧邻目标标号的 \code{GOTO} 后，控制流改为落入下一条 \code{LABEL}：
      省一条 \code{GOTO}，却多计一条 \code{LABEL}，\textbf{动态净收益为 0}，只降低静态行数；
\item O6 删除无引用标号、O8 折叠 \code{GOTO} 链，在执行到相应路径时确实省动态条数；
\item O9 是唯一能在\textbf{假分支}上省一条的规则：它删掉假分支末尾那条 \code{GOTO}
      （真分支路径的执行条数不变）。
\end{itemize}

所以判断一条优化是否有效，看的是\textbf{它在真实执行路径上是否被执行}，而不是它让
文本短了几行。在覆盖必做与选做的语料上实测，优化后动态执行条数合计从
\textbf{3350 降到 2844，降幅 15.1\%}；要求书样例 1 的三种输入分别为 8/8/6 条，
官方“优化后版本”为 10/9/9 条，均不更差。
