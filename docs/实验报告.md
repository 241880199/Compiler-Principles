## 三、亮点 1：`YYSTYPE` 就是 `Node *`

传统写法用 `%union` 为每类终结符声明不同的语义值类型，打印时不得不写"终结符走一条
分支、非终结符走另一条"。本项目让词法单元由 lexer 侧直接构造 `Node *` 交给 parser，
语法单元在 action 里用 `newNode(...)` 组装，于是终结符与非终结符**同构**：

```c
%define api.value.type {Node *}     /* 没有 %union */
```

收益有三：打印器面对**完全同质的树**，遍历代码只有一份；不需要为每种终结符设计语义
值类型；而**实验二要在结点上加符号表字段时，只改 `Node`，遍历代码一行不动**。

一个不可省的设计细节：`Node` 里必须有显式的 `kind` 字段区分终结符与非终结符。
因为 `SEMI`、`LP`、`RP` 这类终结符没有词素（`lexeme == NULL`，与 ε 结点相同），而
ε 结点又是 `nchild == 0`（与终结符相同）——**没有任何间接特征能可靠区分二者**，
靠推测会静默出错。

## 四、亮点 2：非法数字的检出

把"疑似非法"的模式写得比"合法"模式**更长**，用 Flex 的**最长匹配**抢到匹配权，再在
action 内校验。于是三类非法数全部在**词法层**报 type A，且**不依赖规则书写顺序**。

先说清一件事：`09` 既不匹配十进制整数（除 `0` 外首位不为 0）、也不匹配八进制（含
`9`）、也不匹配十六进制；`0x3G`、`1.05e` 同理。**它们不属于任何一个词法单元**，按
要求书 2.1.1 第 1 条即为错误类型 A。要求书给出的 type B 备选答案，是在迁就一个
**未做校验**的简易词法分析器（`09` 被朴素切成 `0` 与 `9`，错误顺延到语法阶段才暴露），
并不是说这个错误的分类本身有歧义。

| 输入 | 谁抢到匹配 | 长度对比 | 校验 | 结果 |
|---|---|---|---|---|
| `0123` | `0[0-9]+` | 4（合法 `0` 仅 1） | 全 ≤7 | `INT: 83` |
| `09` | `0[0-9]+` | 2（合法 `0` 仅 1） | 含 `9` | **type A** |
| `0x3F` | `0[xX][0-9a-zA-Z_]+` | 4 | 全为十六进制位 | `INT: 63` |
| `0x3G` | 同上 | 4（合法规则只能匹配 `0x3`=3） | `G` 非法 | **type A** |
| `1.05e-4` | 合法指数规则 | 7（另一条仅 5） | — | `FLOAT: 0.000105` |
| `1.05e` | 残缺指数规则 | 5（纯小数仅 4） | 后续非数字 | **type A** |

**最隐蔽的一个坑**：十六进制校验规则必须写成 `0[xX](字母|数字)+`，**不能**写成
`0[xX]字母+`。因为"字母"的定义 `[_a-zA-Z]` **不含数字**，写成后者时对 `0x3F` 只能
匹配 3 个字符，比合法规则（4 个字符）**更短**，会被合法规则抢走匹配权——于是 `G`
这类非法字符**永远检测不到**，静默漏报，而检查项看上去是齐的。

一个反直觉的结论：残缺指数规则与合法指数规则的**先后顺序无关**。合法输入下合法规则
必然更长，非法输入下合法规则根本不匹配，二者无需相互顾忌顺序。

## 五、亮点 3：`nodeLine()` —— 一个函数，两件事

语法单元的行号**不在任何 action 里赋值**，而是打印时由结构递归推导：

```c
static int nodeLine(const Node *n) {          /* 子树中第一个词法单元的行号 */
    if (n->kind == NODE_TOKEN) return n->line;            /* 0 表示不含词法单元 */
    for (int i = 0; i < n->nchild; i++) { int l = nodeLine(n->child[i]);
        if (l > 0) return l; }
    return 0;
}
```

词法单元的行号由 lexer 写入一次，是唯一可信来源；语法单元的行号是**结构的函数**，
不是 action 的责任——这消除了"某个产生式忘了写行号"这**一整类** bug。

灵魂在于：要求书说"该单元产生了 ε 则无需打印"。"产生 ε" ⟺ 推不出任何词素 ⟺
**整棵子树不含词法单元** ⟺ `nodeLine` 返回 `0`。**二者是同一件事**，不需要第二个
标志位。

常见错法是用 `nchild == 0` 判 ε：`Program → ExtDefList → ε` 时 `Program` 有**一个**
子结点，会被误判为非 ε，于是打印出一行无关的 `Program (0)`——而行号 `0` 本身就已经
暴露了它其实是 ε。

## 六、亮点 4：错误恢复的同步点，与一处被实测推翻的设计

要求书 2.1.3 要求报告**全部**错误，而 Bison 默认遇错即停，故必须用 `error` 产生式
给出恢复出口。设计原则是：同步点要选在**弹栈越少、丢弃越少**的位置。

最终采用**四个**出口 —— 其中三个带同步符，一个**不带**：

| 出口 | 作用 |
|---|---|
| `Stmt : error SEMI` | 语句层：在 `;` 处同步，使函数体内后续语句仍被检查 |
| `CompSt : error RC` | 块层：在 `}` 处同步，避免一路吞到文件尾 |
| `ExtDef : error SEMI` | 顶层：避免 Bison 弹空栈**中止**而丢掉后面所有错误 |
| **`Def : error`（裸，无同步符）** | 定义层：块内局部定义缺分号时，就地恢复而不丢弃后续内容 |

一处**如实说明**：第四个出口落地后，原第三条 `CompSt : error RC` 的判别力已被它吸收
—— 实测删掉 `CompSt : error RC` 后**冲突数不变、30 个用例仍全过**，另构造的 28 组差分
输入也 **0 组有差异**。本轮**不删**它（删除恢复出口属于行为变更，且它不花额外冲突
代价），但也不声称它仍在起作用：它现在是**无用例守护的保险**。

### 6.0 第四个出口为什么**不能**带同步符（本节结论全靠实测，不靠推演）

块内局部定义缺分号时，`CompSt : LC • DefList StmtList RC` 状态的闭包里**没有**
`error` 出口（`StmtList` 排在 `DefList` **之后**，点在 `DefList` 之前时闭包不展开它
一侧），于是 Bison 一路弹到函数末尾的 `}` 处同步，**同一块内后续错误全被丢弃**。

补一个 `Def` 层的出口能修好它 —— 但**加不加同步符，结果完全不同**，因为 `error`
带同步符时 Bison 会先**丢弃**词法单元直到同步符出现才归约，而裸 `error` 移进后
**立即归约、不丢弃任何前瞻**。四种写法的完整实测（输入为一行为单位，逐字给定）：

| 写法 | 冲突 state | 场景①：块内定义缺分号、块继续 | 场景②：缺分号紧接 `}`、后有兄弟 |
|---|---|---|---|
| **不加（改前）** | 1 | **只报 1 条**（少报） | 报 2 条 |
| `\| error SEMI` | 3 | 报 2 条 | **只报 1 条**（少报） |
| `\| error RC` | 3 | **只报 1 条**（少报） | 报 2 条 |
| **`\| error`（裸）→ 采纳** | **3** | **报 2 条** | **报 2 条** |

两个场景的输入与原始输出：

```
场景①  Test/err/def_resync.cmm            场景②  int main(){ int a } int f(){ int b }（单行）
  1  int main()                             输出（裸 error）：
  2  {                                          Error type B at Line 1: Syntax error.
  3    int a      ← 缺分号                      Error type B at Line 1: Syntax error.
  4    int b;     ← 该行不会被报错
  5    a = 1      ← 缺分号
  6    b = 2;     ← 也不会被报错
  7  }
  输出（裸 error）：
     Error type B at Line 4: Syntax error.
     Error type B at Line 6: Syntax error.
```

**机理**：`error SEMI` 在场景②里把词法单元一路丢到 EOF（整份文件里**一个 `;` 都没有**），
于是只报出第 1 条；`error RC` 则把 `}` 本身当同步符吃掉，块内定义之后的内容整段消失。
裸 `error` 不丢任何东西，`}` 仍在流里、`CompSt → LC DefList StmtList RC` 照常走完。

**这是纯收益**：裸 `error` 引入的 2 个冲突与 `error SEMI` **完全相同**（冲突由 `error`
这个符号本身引起，与后面跟不跟同步符无关），所以"去掉同步符"没有额外代价。
**教训与 6.1 相通**：`error` 产生式后面跟什么，决定的是**丢弃多少**，而"丢弃"才是
少报的来源；不该在无法预知后续内容时选择丢弃。

### 6.1 被实测**否决**的一步（本报告最有个性的部分）

原设计里还有第三条出口 `Exp : error RB`，推演看起来很对：`a[5,3] = 1.5;` 在下标处
出错时就地恢复，正好在 `]` 同步。**实测加入它反而报出 3 条错误**（行 5、行 5、行 6），
直接违反要求书"同一行不出现多个错误"。用 `bison -t` 的调试轨迹查明机理：

1. `Exp LB . Exp RB` 状态的**闭包里就含** `Exp → . error RB`，所以 Bison 在下标
   **内部**就找到了能移进 `error` 的状态，**停止弹栈**——弹栈并没有越过下标；
2. 随后 `error` 规则的同步符 `RB` **恰好就是外层 `[` 正在等待的那个 `]`**；
3. 外层 `[` 从此等不到闭合，语句余下的 `= 1.5;` 全部崩塌 → 同一行冒出第二条错误。

**教训**：设计 `error` 同步点时，不能只看"error 之后想跟什么"，还要看**这个出口是否
已经在当前状态的闭包里**——闭包里有出口时 Bison 会就地停下，**不会**按预期往外弹栈。

去掉它之后，下标内的错误由 `Stmt` 层出口接管，行 5 恰好 1 条、行 6 由 `IF … Stmt .
ELSE` 处暴露 1 条——与要求书的多处错误样例完全一致。

### 6.2 被实测**采纳**的一步：以为要取舍，其实是免费

顶层出口曾被我写成"实测会引入新冲突，代价大于收益"。**这是错的** —— 加上它之后冲突
state 的**数量一个没多**，只是**编号**整体后移（多一条产生式、多两个 state）。实测在

| 文法 | 冲突 state 数 | 悬空 else 所在 state | 总 state 数 |
|---|---|---|---|
| 无 `ExtDef : error SEMI`（旧文法，尚无 `Def : error`） | 1 | 111 | — |
| **有** `ExtDef : error SEMI`（旧文法） | **1** | **113** | — |
| 无 `ExtDef : error SEMI`（**当前**文法，已含 `Def : error`） | **3** | **112** | 116 |
| **有** `ExtDef : error SEMI`（**当前**文法） | **3** | **114** | 118 |

（bison 3.8.2 与评分环境的 3.0.4 两版下**四行的数字都相同**。）即无论哪一代文法，
加上它都是"冲突数不变、编号 +2"。效果：`int a = 1;` 换行 `int b = 2` 从"只报第 1 行"
变为"**两行都报**"。

### 6.3 已试的备选

| 备选 | 冲突数变化 | 结论 |
|---|---|---|
| 裸 `Exp : error` | 1 → 2 | 否决：与 `Stmt`/`CompSt` 层重复，且引入新冲突 |
| `Def : error SEMI` | 1 → 3 | 否决：**会少报**（见 6.0 场景②）。同步符 `SEMI` 使恢复前先丢弃词法单元 |
| `Def : error RC` | 1 → 3 | 否决：**会少报**（见 6.0 场景①）。`}` 被同步符吃掉 |
| **裸 `Def : error`** | 1 → 3 | **采纳**（见 6.0）：不带同步符即不丢弃，两个场景都对 |
| `ExtDef : error SEMI` | 1 → 1（旧文法）<br>3 → 3（当前） | **采纳**（见 6.2）：两代文法下都只是编号后移 |

注意 `Def : error SEMI` 与裸 `Def : error` 的**冲突数变化完全一样**（都是 1 → 3，
且是同样的两个 state）。冲突数与"带不带同步符"无关，它只由 `error` 这个符号本身
引起（`DefList` 可空）。所以这不是取舍 —— **去掉同步符是纯收益**。

## 七、亮点 5：冲突数哨兵

把"冲突数恰好 3"写成测试断言。这 3 处的**归属**（粘自 `syntax.output`，bison 3.8.2
与评分环境的 3.0.4 两版一致）：

```
State 26                              State 31
  32 CompSt: LC • DefList StmtList RC    23 DefList: Def • DefList
  error   shift, and go to state 28      error   shift, and go to state 28
  error   [reduce using rule 24          error   [reduce using rule 24
          (DefList)]     ← 冲突                  (DefList)]     ← 冲突

State 114
  39 Stmt: IF LP Exp RP Stmt •           ← 悬空 else，Bison 默认移进即 C 语义
  40     | IF LP Exp RP Stmt • ELSE Stmt
  ELSE  shift, and go to state 116
  ELSE      [reduce using rule 39 (Stmt)]
```

①② 都是 `Def : error` 引起的同一件事：**`DefList` 可空**，于是"看 `error` 时移进"
与"按 `DefList → ε` 归约"不可兼得。两者都落在 `CompSt` 一路 —— `error` 能跟在
`DefList` 之后，是因为 `StmtList` 可以 `error` 开头（`Stmt : error SEMI`）；
`StructSpecifier : STRUCT OptTag LC • DefList RC`（State 20）**不冲突**，因为结构体
成员表后面只能跟 `RC`，`error` 根本不进它的前瞻集，那里 `error` 是个无歧义的移进。

它守的是一个**任何样例都守不住**的退化——把文法里唯一一行 `%left LB DOT` 删掉后：

| 观察项 | 有该行 | 删掉后 |
|---|---|---|
| 冲突 state 数 | **3** | **13** |
| shift/reduce 冲突数 | 3 | 23 |
| LR 动作表（`yypact`/`yydefact`/`yytable`/`yycheck`/`yystos`/`yyr1`/`yyr2` …） | — | **逐字节完全相同** |
| 30 个用例的逐字节比对 | 全过 | **照样全过** |

即：删掉它之后**程序对外行为一模一样**（"显式声明优先级"与"Bison 默认移进"在这里
恰好得出同一张表）。**除了冲突计数，没有任何测试能发现它被误删。**

顺带点明为何必须有这一行：`LB` 与 `.` 必须显式声明为最高优先级。栈上 `Exp PLUS Exp •`
遇前瞻 `LB` 时，归约得 `(a+b)[1]`、移进得 `a+(b[1])`，**两棵树都合法**，是真实的
shift/reduce 冲突；而 Bison 只在**规则与前瞻 token 都声明了优先级**时才消解，不声明
则这类冲突**根本不进入优先级判定**（实测：只声明其余运算符时 `Exp` 的 100 处冲突只
消掉 80 处，剩下的 20 处正是 `LB`/`DOT` 引起的）。

**"恰好 3 处冲突"不是评分项，而是本项目的哨兵**——它把一个所有样例都察觉不到的静默
退化，变成了一跑就红的断言。**期望值由 1 改成 3 不改变哨兵的语义**（冲突数一变就
报警，不区分"变好"还是"变坏"），只是 3 恰好是当前文法应有的数量。

## 八、已知限制（明知的取舍）

> **本节原有一条限制已被修好并移除，保留记录以备对照。**
>
> **原限制一（已修复）**：局部变量定义处缺分号时，一个语句块内只能报出第一处。
> 例：`int main() { int a` 换行 `int b;` 换行 `a = 1` 换行 `b = 2; }` 实测**只报
> 1 条**（行 4），`int b;` 与 `b = 2;` 的错误全被丢弃 —— 因为缺分号是**定义层**错误，
> `CompSt : LC • DefList StmtList RC` 的闭包里没有 `error` 出口（`StmtList` 排在
> `DefList` **之后**，不在其闭包中），Bison 只能一路弹到函数末尾的 `}` 处同步。
>
> **修复方式**：给 `Def` 补一个**不带同步符**的出口 `Def : error`（第六节 6.0）。
> 关键是**不加同步符** —— 裸 `error` 移进后立即归约、不丢弃前瞻，故块内后续内容照常
> 解析。修复后同一输入实测报 **2 条**（行 4、行 6）。守护它的用例是
> `Test/err/def_resync.cmm`（删掉该产生式后立刻变红）。
>
> **代价**：冲突 state 由 1 变 3（多出的是 `DefList` 可空带来的 2 处，第七节）。
> 因为评分包含多行错误样例，这块覆盖率此时**值过**哨兵的期望值——于是**不削减**
> 哨兵的灵敏度（断言仍在，只是期望值改为 3），而是**照实更新期望值**。

**限制一：同行 type B 抑制可能吞掉一条真实错误。** 实现里有一条"同一行上跟在本条
type A 之后报出的 type B 不打印"的抑制，理由是官方选做样例 2 / 4 的期望输出**只含
type A 行、不含 type B**。判据是按"已报告过的行号"做的**近似，不是因果判断**，故会
误伤：

```
int main() { int a = 1    ← 缺分号（真实错误）
             ~ }          ← 未定义字符（type A）
实测只报 A，那条真实错误被一起吞掉。
```

边界：**符合要求书"同一行不出现多个错误"前提的输入下，本程序仍可能少报一条同行
type B**。判据是**顺序相关**而非因果相关（`int i = 1` 换行 `int j = 09; }` 里 B 先
报出，两条都会打印）。

**其余限制**：不做语义分析、符号表、类型检查（属实验二）；不支持注释嵌套（C-- 明确
不支持，嵌套时在第一个 `*/` 处闭合，其后残留的 `*/` 退化为 type B——这正是要求书
样例的期望行为）；只接受单个输入文件名参数；递归深度未设上限（约 20 万项的左深表达式
会耗尽默认栈），远超出任何合理测试规模。

**最后一条教训值得单独写**：未闭合注释在**词法层**只报一条 type A，但端到端时若
`/*` 位于一个永远无法闭合的函数体内，语法分析器会**额外**报一条 type B。这个差异
最初没有被发现，因为词法单测跑的是 `yylex()`，**根本不经过语法分析器**。
**词法层测过的行为，不等于端到端的行为；单测覆盖了某个模块，不代表该模块在完整
流水线里的表现已被覆盖。**
