## 三、亮点 1：`YYSTYPE` 就是 `Node *`

传统写法用 `%union` 为每类终结符声明不同的语义值类型，打印时不得不写"终结符走一条
分支、非终结符走另一条"。本项目让词法单元由 lexer 侧直接构造 `Node *` 交给 parser，
语法单元在 action 里用 `newNode(...)` 组装，于是终结符与非终结符**同构**：

```c
%define api.value.type {Node *}     /* 没有 %union */
```

收益有三：打印器面对**完全同质的树**，遍历代码只有一份；不需要为每种终结符设计语义
值类型；而**实验二要在结点上加符号表字段时，只改 `Node`，遍历代码一行不动**。

一个不可省的设计细节：`Node` 里必须有显式的 `kind` 字段区分终结符与非终结符。
因为 `SEMI`、`LP`、`RP` 这类终结符没有词素（`lexeme == NULL`，与 ε 结点相同），而
ε 结点又是 `nchild == 0`（与终结符相同）——**没有任何间接特征能可靠区分二者**，
靠推测会静默出错。

## 四、亮点 2：非法数字的检出

把"疑似非法"的模式写得比"合法"模式**更长**，用 Flex 的**最长匹配**抢到匹配权，再在
action 内校验。于是三类非法数全部在**词法层**报 type A，且**不依赖规则书写顺序**。

先说清一件事：`09` 既不匹配十进制整数（除 `0` 外首位不为 0）、也不匹配八进制（含
`9`）、也不匹配十六进制；`0x3G`、`1.05e` 同理。**它们不属于任何一个词法单元**，按
要求书 2.1.1 第 1 条即为错误类型 A。要求书给出的 type B 备选答案，是在迁就一个
**未做校验**的简易词法分析器（`09` 被朴素切成 `0` 与 `9`，错误顺延到语法阶段才暴露），
并不是说这个错误的分类本身有歧义。

| 输入 | 谁抢到匹配 | 长度对比 | 校验 | 结果 |
|---|---|---|---|---|
| `0123` | `0[0-9]+` | 4（合法 `0` 仅 1） | 全 ≤7 | `INT: 83` |
| `09` | `0[0-9]+` | 2（合法 `0` 仅 1） | 含 `9` | **type A** |
| `0x3F` | `0[xX][0-9a-zA-Z_]+` | 4 | 全为十六进制位 | `INT: 63` |
| `0x3G` | 同上 | 4（合法规则只能匹配 `0x3`=3） | `G` 非法 | **type A** |
| `1.05e-4` | 合法指数规则 | 7（另一条仅 5） | — | `FLOAT: 0.000105` |
| `1.05e` | 残缺指数规则 | 5（纯小数仅 4） | 后续非数字 | **type A** |

**最隐蔽的一个坑**：十六进制校验规则必须写成 `0[xX](字母|数字)+`，**不能**写成
`0[xX]字母+`。因为"字母"的定义 `[_a-zA-Z]` **不含数字**，写成后者时对 `0x3F` 只能
匹配 3 个字符，比合法规则（4 个字符）**更短**，会被合法规则抢走匹配权——于是 `G`
这类非法字符**永远检测不到**，静默漏报，而检查项看上去是齐的。

一个反直觉的结论：残缺指数规则与合法指数规则的**先后顺序无关**。合法输入下合法规则
必然更长，非法输入下合法规则根本不匹配，二者无需相互顾忌顺序。

## 五、亮点 3：`nodeLine()` —— 一个函数，两件事

语法单元的行号**不在任何 action 里赋值**，而是打印时由结构递归推导：

```c
static int nodeLine(const Node *n) {          /* 子树中第一个词法单元的行号 */
    if (n->kind == NODE_TOKEN) return n->line;            /* 0 表示不含词法单元 */
    for (int i = 0; i < n->nchild; i++) { int l = nodeLine(n->child[i]);
        if (l > 0) return l; }
    return 0;
}
```

词法单元的行号由 lexer 写入一次，是唯一可信来源；语法单元的行号是**结构的函数**，
不是 action 的责任——这消除了"某个产生式忘了写行号"这**一整类** bug。

灵魂在于：要求书说"该单元产生了 ε 则无需打印"。"产生 ε" ⟺ 推不出任何词素 ⟺
**整棵子树不含词法单元** ⟺ `nodeLine` 返回 `0`。**二者是同一件事**，不需要第二个
标志位。

常见错法是用 `nchild == 0` 判 ε：`Program → ExtDefList → ε` 时 `Program` 有**一个**
子结点，会被误判为非 ε，于是打印出一行无关的 `Program (0)`——而行号 `0` 本身就已经
暴露了它其实是 ε。

## 六、亮点 4：错误恢复的同步点，与一处被实测推翻的设计

要求书 2.1.3 要求报告**全部**错误，而 Bison 默认遇错即停，故必须用 `error` 产生式
给出恢复出口。设计原则是：同步点要选在**弹栈越少、丢弃越少**的位置。

最终采用三个出口：

| 出口 | 作用 |
|---|---|
| `Stmt : error SEMI` | 语句层：在 `;` 处同步，使函数体内后续语句仍被检查 |
| `CompSt : error RC` | 块层：在 `}` 处同步，避免一路吞到文件尾 |
| `ExtDef : error SEMI` | 顶层：避免 Bison 弹空栈**中止**而丢掉后面所有错误 |

### 6.1 被实测**否决**的一步（本报告最有个性的部分）

原设计里还有第三条出口 `Exp : error RB`，推演看起来很对：`a[5,3] = 1.5;` 在下标处
出错时就地恢复，正好在 `]` 同步。**实测加入它反而报出 3 条错误**（行 5、行 5、行 6），
直接违反要求书"同一行不出现多个错误"。用 `bison -t` 的调试轨迹查明机理：

1. `Exp LB . Exp RB` 状态的**闭包里就含** `Exp → . error RB`，所以 Bison 在下标
   **内部**就找到了能移进 `error` 的状态，**停止弹栈**——弹栈并没有越过下标；
2. 随后 `error` 规则的同步符 `RB` **恰好就是外层 `[` 正在等待的那个 `]`**；
3. 外层 `[` 从此等不到闭合，语句余下的 `= 1.5;` 全部崩塌 → 同一行冒出第二条错误。

**教训**：设计 `error` 同步点时，不能只看"error 之后想跟什么"，还要看**这个出口是否
已经在当前状态的闭包里**——闭包里有出口时 Bison 会就地停下，**不会**按预期往外弹栈。

去掉它之后，下标内的错误由 `Stmt` 层出口接管，行 5 恰好 1 条、行 6 由 `IF … Stmt .
ELSE` 处暴露 1 条——与要求书的多处错误样例完全一致。

### 6.2 被实测**采纳**的一步：以为要取舍，其实是免费

顶层出口曾被我写成"实测会引入新冲突，代价大于收益"。**这是错的**——实测在

| 文法 | bison 3.8.2 | bison 3.0.4（评分环境） |
|---|---|---|
| 无 `ExtDef : error SEMI` | `State 111 conflicts: 1 shift/reduce` | 同左 |
| **有** `ExtDef : error SEMI` | `State 113 conflicts: 1 shift/reduce` | 同左 |

两版下冲突数**都仍然恰好 1**，`111 → 113` 只是多出两个 state，不是多一个冲突。效果：
`int a = 1;` 换行 `int b = 2` 从"只报第 1 行"变为"两行都报"。

### 6.3 已试的备选

| 备选 | 冲突数变化 | 结论 |
|---|---|---|
| 裸 `Exp : error` | 1 → 2 | 否决：与 `Stmt`/`CompSt` 层重复，且引入新冲突 |
| `Def : error SEMI` | 1 → 3 | 否决：定义列表可空，"移进"与"按空产生式归约"不可兼得 |
| `ExtDef : error SEMI` | 1 → 1 | **采纳**（见 6.2） |

## 七、亮点 5：冲突数哨兵

把"冲突数恰好 1"（唯一一处是悬空 else，Bison 默认移进即 C 语义）写成测试断言。
它守的是一个**任何样例都守不住**的退化——把文法里唯一一行 `%left LB DOT` 删掉后：

| 观察项 | 有该行 | 删掉后 |
|---|---|---|
| 冲突 state 数 | **1** | **11** |
| shift/reduce 冲突数 | 1 | 21 |
| LR 动作表（`yypact`/`yydefact`/`yytable`/`yycheck`/`yystos`/`yyr1`/`yyr2` …） | — | **逐字节完全相同** |
| 29 个用例的逐字节比对 | 全过 | **照样全过** |

即：删掉它之后**程序对外行为一模一样**（"显式声明优先级"与"Bison 默认移进"在这里
恰好得出同一张表）。**除了冲突计数，没有任何测试能发现它被误删。**

顺带点明为何必须有这一行：`LB` 与 `.` 必须显式声明为最高优先级。栈上 `Exp PLUS Exp •`
遇前瞻 `LB` 时，归约得 `(a+b)[1]`、移进得 `a+(b[1])`，**两棵树都合法**，是真实的
shift/reduce 冲突；而 Bison 只在**规则与前瞻 token 都声明了优先级**时才消解，不声明
则这类冲突**根本不进入优先级判定**（实测：只声明其余运算符时 `Exp` 的 100 处冲突只
消掉 80 处，剩下的 20 处正是 `LB`/`DOT` 引起的）。

**"恰好 1 处冲突"不是评分项，而是本项目的哨兵**——它把一个所有样例都察觉不到的静默
退化，变成了一跑就红的断言。

## 八、已知限制（明知的取舍）

**限制一：局部变量定义处缺分号时，一个语句块内只能报出第一处。** 例：

```
int main() { int a        ← 缺分号
             int b;       ← 不会被报错
             a = 1        ← 缺分号
             b = 2; }     ← 也不会被报错
```

实测只报第 3 行（行号取**触发错误的那个先行词法单元**所在行，不是"缺分号那一行"）。
因为缺分号是**定义层**错误，而 `CompSt : LC • DefList StmtList RC` 状态的闭包里
**没有** `Stmt : • error SEMI`（`StmtList` 排在 `DefList` **之后**，点在 `DefList`
之前时闭包不展开它），Bison 只能一路弹到函数末尾的 `}` 处同步。

**取舍**：要求书只演示了一处多处错误的样例，那是**语句层**错误，本项目已完全覆盖。
补 `Def : error SEMI` 能覆盖上述情形，但实测冲突 state 由 1 变 3 并引入一个真实的
`DefList → ε` 歧义。既然哨兵的灵敏度（第七节）比这块覆盖率更值钱，就保留哨兵、把
限制记录在此。

**限制二：同行 type B 抑制可能吞掉一条真实错误。** 实现里有一条"同一行上跟在本条
type A 之后报出的 type B 不打印"的抑制，理由是官方选做样例 2 / 4 的期望输出**只含
type A 行、不含 type B**。判据是按"已报告过的行号"做的**近似，不是因果判断**，故会
误伤：

```
int main() { int a = 1    ← 缺分号（真实错误）
             ~ }          ← 未定义字符（type A）
实测只报 A，那条真实错误被一起吞掉。
```

边界：**符合要求书"同一行不出现多个错误"前提的输入下，本程序仍可能少报一条同行
type B**。判据是**顺序相关**而非因果相关（`int i = 1` 换行 `int j = 09; }` 里 B 先
报出，两条都会打印）。

**其余限制**：不做语义分析、符号表、类型检查（属实验二）；不支持注释嵌套（C-- 明确
不支持，嵌套时在第一个 `*/` 处闭合，其后残留的 `*/` 退化为 type B——这正是要求书
样例的期望行为）；只接受单个输入文件名参数；递归深度未设上限（约 20 万项的左深表达式
会耗尽默认栈），远超出任何合理测试规模。

**最后一条教训值得单独写**：未闭合注释在**词法层**只报一条 type A，但端到端时若
`/*` 位于一个永远无法闭合的函数体内，语法分析器会**额外**报一条 type B。这个差异
最初没有被发现，因为词法单测跑的是 `yylex()`，**根本不经过语法分析器**。
**词法层测过的行为，不等于端到端的行为；单测覆盖了某个模块，不代表该模块在完整
流水线里的表现已被覆盖。**
