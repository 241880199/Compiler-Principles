## 三、亮点 1：`YYSTYPE` 就是 `Node *`（0.4 页）

**一句话**：终结符与非终结符用**同一个结构**表示，整棵树是同质的，打印器只需要
**一份**遍历代码。

**写法建议**：
1. 传统做法里 `%union` 要为每一类终结符声明不同的语义值类型，打印时不得不写
   "终结符走一条分支、非终结符走另一条"。
2. 本项目的做法：词法单元由 lexer 侧直接构造 `Node *` 交给 parser（`newToken`），
   语法单元在 action 里用 `newNode(...)` 组装，于是 `%define api.value.type {Node *}`。
3. 收益（这三条都要写，是亮点所在）：
   - 打印器面对同质的树，遍历代码只有一份；
   - 不需要 `%union`，也不需要为每种终结符设计语义值类型；
   - 实验二要在结点上加符号表字段时，**只改 `Node`，遍历代码一行不动**。

**可贴的唯一代码（≤5 行）**：`Node` 的字段声明（`src/tree.h`），或 `printTree` 的
递归骨架。二者选一，不要都贴。

**要点名的一个设计细节**：`Node` 里有一个显式的 `kind` 字段区分终结符 / 非终结符——
**它不可省**。因为 `SEMI`、`LP`、`RP` 这类终结符没有词素（`lexeme == NULL`，与 ε
结点相同），而 ε 结点又是 `nchild == 0`（与终结符相同），**没有任何间接特征能可靠
区分二者**，靠推测就会静默出错。

## 四、亮点 2：非法数字的检出（0.5 页）

**一句话**：把"疑似非法"的模式写得比"合法"模式**更长**，用 Flex 的**最长匹配**抢到
匹配权，再在 action 内校验——于是全部三类非法数都在**词法层**报 type A，且**不依赖
规则的书写顺序**。

**核心论证（必须写清，这是本亮点的价值）**：`09` 既不匹配十进制整数（除 `0` 外首位
不为 0）、也不匹配八进制（含 `9`）、也不匹配十六进制，`0x3G`、`1.05e` 同理——
**它们不属于任何一个词法单元**，按实验要求 2.1.1 第 1 条即为错误类型 A。要求书样例
给出的 type B 备选答案，是在迁就一个**未做校验**的简易词法分析器（`09` 被朴素切成
`0` 与 `9`，错误顺延到语法阶段才暴露），并不是说这个错误的分类本身有歧义。

三类各自的机制，用一张表说清（**这是全篇最值得保留的表**）：

| 输入 | 谁抢到了匹配 | 长度对比 | action 内校验 | 结果 |
|---|---|---|---|---|
| `0123` | `0[0-9]+` | 4（合法 `0` 仅 1） | 全 ≤7 | `INT: 83` |
| `09` | `0[0-9]+` | 2（合法 `0` 仅 1） | 含 `9` | **type A** |
| `0x3F` | `0[xX][0-9a-zA-Z_]+` | 4 | 全为十六进制位 | `INT: 63` |
| `0x3G` | 同上 | 4（合法 `0[xX][0-9a-fA-F]+` 只能匹配 `0x3`=3） | `G` 非法 | **type A** |
| `1.05e-4` | 合法指数规则 | 7（另一条仅 5） | — | `FLOAT: 0.000105` |
| `1.05e` | 残缺指数规则 | 5（纯小数仅 4） | 后续非数字 | **type A** |

**要点名最隐蔽的那个坑**：十六进制校验规则必须写成 `0[xX](字母|数字)+`，**不能**
写成 `0[xX]字母+`。因为"字母"的定义 `[_a-zA-Z]` **不含数字**，写成后者时对 `0x3F`
只能匹配 3 个字符，比合法规则（4 个字符）**更短**，会被合法规则抢走匹配权，于是
`G` 这类非法字符**永远检测不到**——静默漏报，样例却照过。

**再补一句"反直觉"的结论**：残缺指数规则与合法指数规则的**先后顺序无关**——
合法输入下合法规则必然更长，非法输入下合法规则根本不匹配，二者无需相互顾忌顺序。

## 五、亮点 3：`nodeLine()` —— 一个函数同时承担行号推导与 ε 判定（0.4 页）

**一句话**：语法单元的行号**不在任何 action 里赋值**，而是打印时由结构递归推导；
推导函数的返回值 `0` **同时就是"该结点产生了 ε"的判定**，不需要第二个标志位。

**行号的定义**（要求书）：该语法单元产生出的所有词素中**第一个**在输入文件中出现的
行号。→ 于是 `nodeLine(n)` 返回"子树中第一个词法单元的行号"，词法单元的行号**只由
lexer 写入一次**，是唯一可信来源。

**收益**：这消除了"某个产生式的 action 忘了写行号"这**一整类** bug——行号是结构
的函数，不是 action 的责任。

**关键洞察（本亮点的灵魂，必须写）**：
"该单元产生了 ε" ⟺ 该单元推不出任何词素 ⟺ **其整棵子树不含词法单元** ⟺
`nodeLine` 返回 `0`。二者是**同一件事**，所以不需要额外的 ε 标志位。

**点名一个常见错法**：用 `nchild == 0` 判 ε 是**错的**。`Program → ExtDefList → ε`
时 `Program` 有**一个**子结点，按 `nchild == 0` 会被误判为非 ε，于是打印出一行
`Program (0)` —— 而行号 `0` 本身就已经暴露了它其实是 ε。用 `nodeLine == 0` 判定则
天然正确。

**可贴的唯一代码（≤5 行）**：`nodeLine` 的递归主体（`src/tree.c`）。

## 六、亮点 4：错误恢复的同步点设计，与一处被实测推翻的设计（0.6 页）

**这是全篇最有分量的部分，篇幅给足。**

### 6.1 为什么需要它

要求书 2.1.3 要求报告**全部**错误，但同一个错误行中**不出现多个**错误。Bison 默认
遇错即停，故必须用 `error` 产生式给出恢复出口。

### 6.2 最终采用的四个出口（三个带同步符、一个不带）

| 出口 | 作用 |
|---|---|
| `Stmt : error SEMI` | 语句层：弹到最近的 `Stmt` 出口，丢弃出错的一段，在 `;` 处同步，使函数体内**后续语句**仍能被检查 |
| `CompSt : error RC` | 块层兜底：`{` 之后出现无法归入 定义/语句 的内容时，在 `}` 处同步，避免一路吞到文件尾 |
| `ExtDef : error SEMI` | 顶层：顶层出错后在 `;` 处同步，避免 Bison 弹空栈**中止**、把后面所有错误丢掉 |
| **`Def : error`（裸，无同步符）** | 定义层：块内局部定义缺分号时就地恢复，避免弹到函数末尾的 `}`、丢掉同块后续错误 |

**设计原则（一句话点透）**：同步点要选在**弹栈越少、丢弃越少**的位置。出口越靠近
出错点，被连带丢弃的正确代码就越少。

**第四个出口的额外教训（值得单独写）**：`Def` 层的出口**必须不带同步符**。带同步符时
Bison 会先**丢弃**词法单元直到同步符出现才归约；裸 `error` 移进后**立即归约、不丢弃
任何前瞻**。实测四种写法（两个场景都必须正确报出 2 条）：

| 写法 | 冲突 state | 块内定义缺分号、块继续 | 缺分号紧接 `}`、后有兄弟 |
|---|---|---|---|
| 不加 | 1 | 只报 1 条（少报） | 报 2 条 |
| `\| error SEMI` | 3 | 报 2 条 | 只报 1 条（少报，整份文件无 `;` 时丢到 EOF） |
| `\| error RC` | 3 | 只报 1 条（少报，`}` 被同步符吃掉） | 报 2 条 |
| **`\| error`（裸）→ 采纳** | **3** | **报 2 条** | **报 2 条** |

关键点：裸 `error` 与 `error SEMI` 引入的冲突**完全一样**（都是 1 → 3、同样的两个
state，因为冲突由 `error` 符号本身引起，与后面跟不跟同步符无关）。所以**去掉同步符
是纯收益，不是取舍** —— 这一点让"加出口要付冲突代价"的顾虑消失。

**顶层那个出口曾被误判为"要付冲突代价"** —— 设计文档原写作"给 `ExtDef` 层加 `error`
出口实测会引入新冲突，冲突数必须保持 1，代价大于收益"。**这是错的**：加上它之后
冲突 state 的**数量一个没多**，只是**编号**整体后移（多了一条产生式、多出两个 state）。

实测数据（两个版本的 Bison 结论一致）：

| 文法 | 冲突 state 数 | 悬空 else 所在 state | 总 state 数 |
|---|---|---|---|
| 无 `ExtDef : error SEMI`（旧文法，尚无 `Def : error`） | 1 | 111 | — |
| 有 `ExtDef : error SEMI`（旧文法） | **1** | **113** | — |
| 无 `ExtDef : error SEMI`（**当前**文法，已含 `Def : error`） | **3** | **112** | 116 |
| 有 `ExtDef : error SEMI`（**当前**文法） | **3** | **114** | 118 |

即：无论哪一代文法，加上它都是"**冲突数不变、编号 +2**"。当前文法下冲突数为 3
（`Def : error` 的 2 处 + 悬空 else 1 处），去掉顶层出口后仍是 3（只是编号变成
24 / 29 / 112）。所以它不是取舍，是免费。

效果（`Test/err/toplevel_resync.cmm`）：输入 `int a = 1;` 换行 `int b = 2` —— 修复前
只报第 1 行（第 2 行被中止吞掉），修复后**两行都报**（实测 `.exp` 即
`Error type B at Line 1.` + `Error type B at Line 2.`）。这是"**以为要取舍、其实是免费**"
的第二个例子，与本节的 `Exp : error RB` 正好相反：一个靠实测被**否决**，一个靠实测
被**采纳**。

### 6.3 被实测推翻的一步（**本报告的"独创性"内核**）

原设计里还有第三条出口 `Exp : error RB`，其推演看起来很对：`a[5,3] = 1.5;` 的
`a[5,3]` 处出错时，就地在下标内部恢复，正好在 `]` 处同步。

**实测加入它反而报出 3 条错误**（行 5、行 5、行 6），直接违反"同一行不出现多个错误"。
用 `bison -t` + 调试轨迹查明机理：

1. `Exp LB . Exp RB` 状态的**闭包里就含** `Exp → . error RB`，所以 Bison 在下标
   **内部**就找到了能移进 `error` 的状态，**停止弹栈**——弹栈并没有越过下标；
2. 随后 `error` 规则的同步符 `RB` **恰好就是外层 `[` 正在等待的那个 `]`**，被这个
   内层错误规则吃掉；
3. 外层 `[` 从此永远等不到闭合，语句余下的 `= 1.5;` 全部崩塌 → 同一行冒出第二条错误。

**要提炼出的教训（这是最值得写进报告的一句）**：设计 `error` 同步点时，不能只看
"error 之后想跟什么"，还要看**这个出口是否已经在当前状态的闭包里**——闭包里有出口
时 Bison 会就地停下，**不会**按预期往外弹栈。

**去掉它之后**：下标内的错误由 `Stmt` 层出口接管，丢弃整条语句后在 `;` 同步。行 5
恰好 1 条，行 6 由 `IF … Stmt . ELSE` 处暴露、1 条——与要求书多处错误样例完全一致。

### 6.4 已试的备选（用表格，各一行）

表中的"冲突数变化"是在**该式加入之前**的文法上实测的增量。

| 备选 | 冲突数变化 | 结论 |
|---|---|---|
| 裸 `Exp : error` | 1 → 2 | 否决：与 `Stmt`/`CompSt` 层出口重复，且引入新冲突 |
| `Def : error SEMI` | 1 → 3 | 否决：**会少报**（见 §6.2 表）。同步符使恢复前先丢弃词法单元 |
| `Def : error RC` | 1 → 3 | 否决：**会少报**（见 §6.2 表）。`}` 被同步符吃掉 |
| **裸 `Def : error`** | 1 → 3 | **采纳**（见 §6.2）：不带同步符即不丢弃，两个场景都对 |
| `ExtDef : error SEMI` | 1 → 1 | **采纳**（见 §6.2）：原以为会增加冲突，实测只是编号后移 |

**注意 `Def : error SEMI` 与裸 `Def : error` 的冲突增量完全相同**（都是 1 → 3，
且是同样的 `CompSt: LC • DefList StmtList RC` 与 `DefList: Def • DefList` 两个
state）。冲突由 `error` 这个**符号本身**引起（`DefList` 可空 → "移进 `error`"与
"按 `DefList → ε` 归约"不可兼得），与后面跟不跟同步符无关。**故"去掉同步符"是纯
收益，不额外付冲突代价** —— 这一条是本轮最主要的修正。

**这一节的价值在于展示"推演—实测—修正"的完整闭环**，而不是展示最终答案。

## 七、亮点 5：冲突数哨兵（0.3 页）

**一句话**：把"冲突数恰好 3"写成测试断言，它守的是一个**任何样例都守不住**的退化。

**这 3 处的归属**（粘自 `syntax.output`，两版 Bison 一致）：State 26
（`CompSt: LC • DefList StmtList RC`）与 State 31（`DefList: Def • DefList`）是
`Def : error` 引起的一对 —— 两者都是"移进 `error`"与"按 `DefList → ε` 归约"之争；
State 114 是悬空 else。`StructSpecifier : STRUCT OptTag LC • DefList RC`（State 20）
**不冲突**：结构体成员表后面只能跟 `RC`，`error` 不进它的前瞻集。

**硬证据（本仓库实测，可直接引用）**：把文法里唯一一行 `%left LB DOT` 删掉后——

| 观察项 | 有 `%left LB DOT` | 删掉后 |
|---|---|---|
| 冲突 state 数 | **3** | **13** |
| shift/reduce 冲突数 | 3 | 23 |
| LR 动作表 `yypact/yydefact/yypgoto/yydefgoto/yytable/yycheck/yystos/yyr1/yyr2` | — | **逐字节完全相同** |
| 30 个用例的 `.exp` 比对 | 全过 | **照样全过**（唯一红的是冲突数断言本身） |

即：删掉它以后，**程序对外行为一模一样**——因为"显式声明优先级"和"Bison 默认移进"
在这里恰好得出同一张表。**除了冲突计数，没有任何测试能发现它被误删。**

**顺带点明为什么需要这一行**：`LB` 与 `.` 必须显式声明为最高优先级。栈上
`Exp PLUS Exp •` 遇前瞻 `LB` 时，归约得 `(a + b)[1]`、移进得 `a + (b[1])`，
**两棵树都合法**，是真实的 shift/reduce 冲突；而 Bison 只在**规则与前瞻 token 都
声明了优先级**时才用优先级消解，不声明则这类冲突**根本不进入优先级判定**，声明多少
别的运算符都消不掉（实测：只声明其余运算符时 `Exp` 的 100 处冲突只消掉 80 处，
剩下的 20 处正是 `LB`/`DOT` 引起的）。

**要提炼的教训**：**"恰好 3 处冲突"不是评分项，而是本项目的哨兵**——它把一个
"所有样例都察觉不到"的静默退化，变成了一个一跑就红的断言。**期望值由 1 改成 3
不改变哨兵的语义**（冲突数一变就报警，不区分"变好"还是"变坏"），只是 3 恰好是当前
文法应有的数量。

## 八、已知限制（0.3 页）

**写成"明知的取舍"，不要写成"已知 bug"**——每条都要给出取舍依据。

> **本节原有的一条主限制已被修好并移除，建议保留一句记录以备对照。**
>
> **原主限制（已修复）**：局部变量定义处缺分号时，一个语句块内只能报出第一处 ——
> `int main() { int a` 换行 `int b;` 换行 `a = 1` 换行 `b = 2; }` 实测**只报 1 条**，
> 因为 `CompSt : LC • DefList StmtList RC` 的闭包里没有 `error` 出口（`StmtList` 排在
> `DefList` **之后**），Bison 只能弹到函数末尾的 `}` 处同步。
>
> **修复**：给 `Def` 补一个**不带同步符**的出口 `Def : error`（见 §6.2）。关键是
> **不加同步符**：裸 `error` 立即归约、不丢弃前瞻，故块内后续内容照常解析。修复后
> 同一输入实测报 **2 条**（`Test/err/def_resync.cmm` 守护，删掉该式立刻变红）。
> 代价是冲突 state 由 1 变 3 —— 因为评分包含多行错误样例，这块覆盖率此时值过哨兵的
> 期望值，于是**不削减**哨兵灵敏度（断言仍在），只**照实更新期望值**。

**当前唯一的实质限制：同行 type B 抑制可能吞掉一条真实错误。** 实现里有一条"同一行上跟在本条
type A 之后报出的 type B 不打印"的抑制（理由见 §7.4(1)：官方选做样例 2/4 的期望输出
只含 type A 行、不含 type B）。**判据是按"已报告过的行号"做的近似，不是因果判断**，
所以它也会误伤：

```
int main() { int a = 1      ← 缺分号（真实错误）
             ~ }            ← 未定义字符（type A）
}
实测只报 A4，那条真实缺分号错误被一起吞掉。
```

边界要说清：**符合要求书"同一行不出现多个错误"前提的输入下，本程序仍可能少报一条
同行 type B**；判据是**顺序相关**的（`int i = 1` 换行 `int j = 09; }` 里 B 先报出，
两条都会打印），不是因果相关。

**其余可各写一行**：
- 不实现语义分析、符号表、类型检查（属于实验二）；
- 不支持注释嵌套（C-- 明确不支持，嵌套时在第一个 `*/` 处闭合，其后残留的 `*/`
  退化为类型 B 的语法错误——这正是要求书样例的期望行为）；
- 只接受单个输入文件名参数；
- 嵌套注释的"未闭合"只保证在**词法层**报一条 type A；端到端时若 `/*` 位于一个永远
  无法闭合的函数体内，语法分析器会**额外**报一条 type B。这一点是词法单测与端到端
  实测结论不一致的地方，值得作为"教训"一句话带过：**词法层测过的行为，不等于端到端
  的行为；单测覆盖了某个模块，不代表该模块在完整流水线里的表现已被覆盖。**
