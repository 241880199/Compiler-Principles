其中十种情形\textbf{要求书与指导书都没有规定}（变量名与函数名冲突报哪个码？形参与函数体算不算同一层？同一行出现两条错误留哪一条？）。这些没有依据可查，只能自己选定一种行为；实现上把每一条都收敛在代码里的\textbf{一个位置}（一个 \code{if}、一处查表项、一个函数），并各配一个专属用例，于是改动某一条时只动一处、且立刻有一条用例会变红。

\section*{二、如何编译}

\begin{lstlisting}[language=bash]
sudo apt-get install -y flex bison gcc make
make clean && make          # 生成 ./parser（同时生成同内容的 ./cc）
./parser <文件>              # 无错时不输出任何内容；有错时打印错误信息
\end{lstlisting}

编译与实验一完全相同：仓库根目录执行 \code{make} 即可，除 \code{src/} 外不依赖任何
目录。\textbf{请勿使用 \code{make -j}} —— \code{syntax.tab.c syntax.tab.h} 是一条
「一个 recipe、两个目标」的多目标规则，并发下会被当成两条独立规则、同时跑两次 bison
并写同一个文件。

关于 Bison 版本：文法不使用 3.1 以后才引入的写法（不用
\code{\%define parse.error detailed}、不用 \code{\%union}），因此 \textbf{3.0.4 及
以上各版本均可编译}。冲突 state 的编号只取决于文法本身，与 Bison 版本无关；本报告凡是
提到编号的地方都标了它对应的文法形态。

\section*{三、亮点 1：语义分析做成一遍独立的后序遍历，而不是在文法 action 里顺手做}

最自然的做法是\textbf{语法制导翻译}：在 Bison 的 action 里当场检查、当场登记符号。它
省掉一趟遍历，也省掉保存整棵语法树的内存；对「每条规则只做一件小事」的检查（例如
「下标的类型必须是 \code{int}」）确实够用。指导书 §3.2.5 建议改走另一条路 ——「Bison
代码只用于构造语法树，而把和语义分析相关的代码都放到一个单独的文件中去」，我们采用
这条路线。不过建议只给到骨架：\textbf{它在本实验里不只是「更好组织」，而是被要求逼出来
的}，而走上这条路之后内部还有三处必须自己拿准。

先说为什么非改不可 —— 照最自然的写法，本实验有两类检查做不了或做不好。

一类是\textbf{必须自上而下携带的上下文}。错误 8 要拿 \code{return} 后面那个表达式的类型
与\textbf{所在函数}的返回类型比对，而后者不在那条语句的子树里。纯自底向上、只用综合属性
的写法得为它额外挂一个全局量，函数的进出还要靠文法规则的归约时刻去维护 —— 与下面那类是
同一个麻烦。在我们的结构里它只是遍历途中的一个 \code{curFuncReturn}：进函数体时置上、
出函数体时清掉。

另一类是\textbf{作用域}。语法制导翻译要求把「进入/退出一个作用域」精确地插进文法规则的
时序里，而规则的归约时刻与「作用域何时结束」并不天然对齐：函数体与语句块该在哪条产生式
的 action 上进入，会不会被错误恢复打乱，都要逐条推敲。

所以我们把两件事\textbf{分开}：前端沿用实验一的 Flex + Bison，语义分析\textbf{完全
手写}，在实验一已经建好的语法树上做一遍后序遍历。为此文法只加了\textbf{一条}产生式，
而它在本版本里唯一的作用是\textbf{在动作里拒绝函数声明}（见第一节"选做的取舍"）——
不承担任何语义工作。这条产生式只新增 1 个 state，\textbf{冲突个数不变}（仍是 3）。
上面两类上下文于是都退化成遍历途中的普通变量 ——
\code{curFuncReturn} 与当前作用域；作用域的进出收敛成\textbf{两个}调用点（函数体、
语句块），每条检查只读自己子树上的信息。举一处只有这种结构才写得干净的例子：左值判据（赋值号
左边只能是 \code{ID}、\code{Exp LB Exp RB} 或 \code{Exp DOT ID}）是\textbf{结点形状}的
判断，直接问结构即可，不必推敲归约顺序。

前端与语义层的交界也只有一个判据：整棵树语法分析走完（没有 \code{A}/\code{B} 错误）
才进入语义分析，否则只把词法单元读到 EOF 以保证词法错误不丢。

代价是整棵树的内存与一趟遍历，本实验的输入规模下都可忽略；换来的是\textbf{检查与文法
解耦} —— 改一条检查不用碰文法，新增一条检查也不会连锁影响别的检查。

\section*{四、亮点 2：符号表是「一张散列表加十字链表」，而不是每层作用域一张表}

普通做法是\textbf{每层作用域一张独立的表}：进入作用域 push 一张空表，退出 pop 并销毁，
查名字从最内层向外层\textbf{逐张查、命中即停}。它的优点很实在 —— 「只查当前作用域」
（判重复定义）就是查当前那张表，一步到位。指导书 §3.2.2/§3.2.3 给了另一套结构
（十字链表 + open hashing：同一批条目同时挂在「本层链表」与「散列槽」两条链上），我们
采用它。两套结构都能跑通选做 2.2，差别在于\textbf{遮蔽语义靠什么来保证} —— 这是本节要说
的，也是把结构定下来之后必须自己拿准的地方。

但在它那里，遮蔽语义成了\textbf{循环次序的产物}。查名字必须「由内向外、命中即停」，
这个次序写反（或漏了一层）时，程序会把外层的定义当成内层的；而这类错误在\textbf{只有
一处同名定义}的输入上完全没有症状 —— 没有同名就谈不上遮蔽，两个方向的循环给出同一个
答案（要求书选做 2.2 的样例正是要区分这种情形）。同理，退出作用域时若忘了销毁/隔离那张
表，名字会「泄漏」到外层，而这同样只在「外层恰好有同名」时才看得见。

我们用的是一张散列表、项上自带深度，再用\textbf{十字链表}把同一批条目同时组织成两条链：

\begin{itemize}
\item \textbf{同层链}（\code{scopeHead[depth]}）—— 回答「当前作用域里有没有这个名字」
（判重复定义用），只走本层；
\item \textbf{同槽链}（\code{buckets[h]}）—— 回答「由内向外第一个可见的定义」。
\end{itemize}

关键在于槽内链\textbf{按插入顺序}：最新插入的（因而最深、最内层）在\textbf{链头}。
于是一次线性走链、返回\textbf{第一个 \code{depth} $\le$ 当前深度}的项，拿到的就恰好是
最内层的定义 —— 遮蔽不再是循环次序的产物，而是\textbf{一条判据}的直接后果。深度也不再
是「它待在哪张表里」这种隐含信息，而是项自己的字段，随时可查。

退出一层作用域只做「摘同层链」，不动散列表结构；两个查询各有自己的链，都不必逐层循环。
四个入口把结构封在后面：调用方问的是「由内向外第一个可见定义」，而不是「第几层表的第
几个槽」。

\section*{五、亮点 3：一个在语义层\textbf{观测不到}的 bug，决定了模块边界}

普通做法是\textbf{照收集顺序折叠数组维度}，而 \code{VarDec} 是左递归的 —— 最外层的
结点带的是\textbf{最后一个}方括号：

\begin{lstlisting}[language=C]
VarDec( a[10][2] ) = VarDec( VarDec( a ) LB 10 RB ) LB 2 RB
\end{lstlisting}

而 C 语义要求\textbf{第一个}方括号才是最外维（\code{a} 是「10 个 \code{int[2]}」）。
照收集顺序从左往右折，得到的是 \code{array(2, array(10, int))}：\textbf{维度顺序反了}。

这个错误在本实验里\textbf{没有任何症状}：要求书的数组等价\textbf{忽略长度}，反了的数组
与任何同维数组比较仍然「相等」；\textbf{维数没变}，于是错误 10（对非数组用 \code{[]}）
的触发条件不变；错误 12 只看\textbf{下标}的类型，与数组本身是什么类型无关。也就是说，
17 种检查\textbf{一条都发现不了它} —— 整棵语法树、整条遍历路径上，没有任何可观测量能
反映它。

唯一能钉住它的办法，是让类型模块\textbf{脱离词法、语法、符号表独立可测}，并且断言
\textbf{具体的 \code{size} 值}（只查维数同样抓不到）。这就是这条模块边界的由来：
\code{type.c} \textbf{不依赖任何东西}（连符号表都不依赖），不是为了分层好看，而是因为
\textbf{只有它能看见这个 bug}。

一句话：\textbf{判别力的边界决定模块的边界} —— 一个错误若在高层没有任何可观测量，就
只能靠把低层做成可独立测试的纯模块来发现。这也是整个实验二里唯一一处「模块怎么切」是
由\textbf{可观测性}、而不是由功能划分决定的。
